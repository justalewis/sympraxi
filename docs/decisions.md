# Technical decisions

Short records of choices made while building, with the reason, so later contributors don't have to guess. Newest first.

## Accessibility checks on phones, after htmx updates and with emulated settings (October 2026)

The accessibility notes listed three states axe never saw: a phone-sized screen with the menu open, content htmx swaps in, and forced colors or reduced motion. `tests/e2e/test_accessibility.py` now checks each. axe found one problem, in the menu's close button.

**Phone size is 375 by 812, with touch.** That is a common phone's viewport in CSS pixels. The browser context also says it is a mobile device with a touch screen, so the page lays out as on a phone and the menu opens with a tap. Eight student pages are checked: signing in, My centers, the center page, a day's open times, booking, my appointments, one appointment and a session on My writing. axe runs on each twice, as the page loads and with the menu open, because the open menu's overlay covers the page and axe can't check the contrast of anything under it. Before the second run the test waits for the menu to finish sliding in.

**A script checks the menu's focus trap, because axe can't.** While the menu is open, USWDS puts `aria-hidden` on everything outside it, so screen readers skip the page behind it. The links back there can still take focus, and axe can't tell whether Tab reaches them, so it marks its `aria-hidden-focus` rule as needing review instead of passing or failing it. USWDS's focus trap is what keeps them out of reach. `test_the_phone_menu_keeps_focus_inside_until_closed` opens the menu by keyboard, presses Tab and Shift+Tab, and fails if focus leaves the menu. It also checks that Escape closes the menu, puts focus back on the Menu button and takes `aria-hidden` off the page. Using the `inert` attribute instead would mean JavaScript of Sympraxi's own, which it doesn't ship.

**The htmx checks reuse the keyboard tests' steps.** The steps that make htmx swap content in are functions shared by the keyboard tests and `test_swapped_in_content_passes_axe`: changing the date on open times and on the page for moving an appointment, choosing an answer that has a follow-up question, tagging a topic and attaching the suggested resource, searching the resources and the members, and moving a question. Sharing them keeps the two sets of tests from drifting apart. axe runs after each step, once htmx has no request out and has finished settling, since some changes (hiding "Nothing attached yet," for one) happen only after its settle delay. The test also fails if the page reloaded, so a broken htmx attribute can't pass by falling back to a full page that was already tested.

**Forced colors and reduced motion run separately.** Playwright's `forced_colors="active"` and `reduced_motion="reduce"` change which media queries Chromium matches. Eight pages that between them use most of the USWDS components Sympraxi does are checked under each, one setting at a time so a failure names it, and each test first checks that the media query matches, so it can't pass after the emulation stops working. The open phone menu is checked under each too, since USWDS's styles for both settings change it: under forced colors the close button's image is swapped for a drawn X, and under reduced motion the menu no longer slides in. That test fails if anything is animating right after the menu opens.

**axe's color rules are off under forced colors.** With forced colors, axe compares the page's own text colors with the forced background rather than the colors the browser draws. Under a dark theme it reported near-black text on black on every page, though the screenshots showed white and yellow on black; under a light theme the same mistake passes by luck. So `color-contrast` and `link-in-text-block` are turned off in those runs, and contrast in a real Windows contrast theme stays a manual check. The other rules still run, and one of them caught the close button below, because USWDS's forced-colors styles hide some elements and draw others.

**The menu's close button is named by hidden text.** Its name came from the alt text of its X image. Under forced colors USWDS hides that image and draws the X with CSS instead, so in a contrast theme the button had no accessible name. The image now has empty alt text, and the button holds "Close menu" in a `usa-sr-only` span, which forced colors leave alone.

## Fixes from the security and accessibility drafts (October 2026)

Drafting the HECVAT answers (`docs/security-questionnaire.md`) and the accessibility notes (`docs/accessibility.md`) turned up gaps that could be closed in code. These are the choices made in closing them.

**Two-factor secrets are encrypted in the database.** allauth stores each authenticator app's TOTP secret, and the seed the recovery codes are made from, in `mfa_authenticator.data`, and its default MFA adapter stores them as they are. Anyone with a database dump or a backup could then make any person's codes, and a site administrator could read them in the Django admin. `MFAAdapter` now encrypts them with Fernet (AES-128 in CBC mode with an HMAC-SHA256 tag, from the `cryptography` package) before allauth saves them (`sympraxi/accounts/encryption.py`). Accounts migration 0004 encrypts the ones stored before it and skips any that are already encrypted. Passkeys hold only a public key and aren't changed. The secret allauth keeps in the session while someone is setting up an app isn't covered: it can't sign anyone in until they confirm a code, and allauth drops it then.

**The key comes from SECRET_KEY.** A separate key would sit next to SECRET_KEY in `deploy/.env`, with the same readers, so it would protect nothing more and be one more thing to lose. The Fernet key is derived from SECRET_KEY with HKDF and a label used for nothing else, so it never equals the key Django signs with. A backup restored without the SECRET_KEY it was made under therefore leaves every authenticator app and recovery code unreadable, for the campus as for a thief, so install.md says to keep a copy of the key.

**Changing the key uses Django's fallbacks.** `SYMPRAXI_SECRET_KEY_FALLBACKS` sets `SECRET_KEY_FALLBACKS`. Secrets written under a fallback still decrypt, and `manage.py reencrypt_mfa_secrets` rewrites them under the current key, after which the fallback can go. Django uses the same setting to keep sessions and reset links working during the change. A secret no key can read makes the code check fail with a server error whose log message names the setting, instead of quietly calling every code wrong. If the old key is lost, `--remove-unreadable` deletes those authenticators and records each removal in the audit log, and their owners set up two-factor login again.

**Checkboxes show their hint and their error.** `includes/field.html` drew a checkbox with only its label. Its help text and its error never appeared, though the box's `aria-describedby` already pointed at a hint that wasn't there. The form builder's error for a required demographic question was one nobody saw: the page came back with no message. The hint now sits under the label, lined up with the label's text, and an error puts the box in a USWDS error group with the message above it. Both are tied to the box as other fields' are, and a test checks that `aria-describedby` never names an element missing from the page. The question form's checkbox hints, which were loose paragraphs, now come from the field. allauth's own field element ties its errors to the input the same way.

**Error pages use the site's layout and show nothing from the request.** Django's plain 403, 404, 500 and CSRF pages had no header, navigation or way back. `403.html`, `404.html`, `500.html` and `403_csrf.html` now extend `base.html`. The 404 page doesn't show the path or the exception, so a student who opens another student's appointment gets the same page, byte for byte apart from the CSRF token and the CSP nonce, as for an appointment that doesn't exist; a test compares the two, and a third from another center. The 500 page is rendered without the request's context (`core.views.server_error`), as Django's own handler does, because the user, session and message context processors read the database, which may be what failed. It gets only the site name, so its navigation offers just the home page. A failed CSRF check has its own view (`CSRF_FAILURE_VIEW`), because Django's default renders the template without the request's context. Its page says nothing was saved and what usually causes it; the reason goes only to Django's log.

**The rest of allauth's pages are axe-tested.** The browser tests covered allauth's sign-in, sign-up, password and two-factor settings pages, but no others. `ACCOUNT_PAGES` in `tests/e2e/test_accessibility.py` adds 21: the password-reset steps after the email, email confirmation, the two-factor code at sign-in, signing out, reauthenticating with a password or a code, setting a password on an account made by single sign-on, setting up an authenticator app, recovery codes, passkeys (the list, adding, editing and removing one), an inactive account and a failed SSO sign-in. Pages that want a recent sign-in are opened after signing in through the real forms (the `sign_in_with_password` fixture), and the test fails if a page sends the browser anywhere else, such as back to sign in. Two problems turned up, both on the passkey list. allauth's template loads Django's `humanize` tags, which weren't installed, so the page was a server error for anyone with a passkey; `django.contrib.humanize` is installed now. And its column of Edit and Remove links had an empty header; Sympraxi's copy of the template names the column for screen readers and puts each key's name in its links. Not covered: the SSO sign-up page, which allauth shows only when a provider's sign-in lacks something it needs, and signing in with a passkey, which happens in the browser's own dialog.

**Forms with errors are axe-tested.** axe saw each page only as it first loaded. `FORMS_WITH_ERRORS` fills in and sends forms the way a person would and runs axe on the page that comes back: sign-up with a short password, sign-in with a wrong one, the booking page without the required intake answers, and a demographic question marked required. Each form passes the browser's own checks for required fields, so the errors tested are the ones the server sends back.

**People change their own name and pronouns.** Only a site administrator could, in the Django admin, so a student whose name or pronouns changed had to ask someone. Account now opens on Name and pronouns (`accounts:profile`), for everyone signed in. It changes the full name, the preferred name and the pronouns and nothing else; the email address keeps allauth's page and its confirmation step. Each change is recorded as `auth.profile_changed`, naming the fields that changed but not what they said before or after, like the other account events. The full name stays editable for accounts made by single sign-on too: Sympraxi copies it from the provider only when it creates the account, so a sign-in never overwrites a change. The page is on the axe list, and on the list of forms sent back with errors, with a blank full name.

**Backups still leave out the two settings files.** `deploy/.env` holds the key that decrypts the two-factor secrets, and `deploy/backup.env` holds the restic password. A backup that carried them would carry the keys that protect it, and anyone holding one backup folder would have everything needed to read it. So `backup.sh` still leaves them out, and install.md now says to keep a copy of both away from the server, what each holds, what a restore onto a new server needs, and how to change the secret key and the database password. `install.sh` now makes `backup.env` readable only by its owner, as it already did `deploy/.env`.

## Phase 1: session-report questions and surveys (October 2026)

**Report answers belong to the record.** A center has one set of session-report questions, built like its other forms. They show on the record form below the fixed fields, and the tutor answers them. Each record has at most one response (`Response.record`), about the record's student, stored by question and option key like every other answer, so reports can count them across versions.

**Drafts replace their answers; final records amend them.** There were two ways to let a draft's answers change: a new response on every save, or an exception to the append-only trigger for drafts. Sympraxi takes the exception (forms migration 0004). While a record is a draft, each save deletes its response and writes a new one on the version the center asks now. A new response per save would have kept, permanently and in the FERPA export, answers a tutor changed before finalizing, while the record's own draft text is simply overwritten; and every report would have had to find the latest response for each record. Once the record is final, the trigger refuses any change to its answers unless the transaction has opened an amendment for that record, the same test records migration 0002 uses. `services.amend()` changes the answers in place, on the version they were given in, and keeps each changed one in the amendment under `answer:<question key>`, with the question and the answer before and after in words. The response itself never changes, and a final record can't gain a second one.

**Finalizing needs the required questions that show.** A required follow-up counts only when its condition is met. On a draft, required questions are marked "needed to finalize" and not refused, like the summary. An amendment keeps them required. Questions taken out of use aren't asked and aren't needed.

**An amendment asks the version the record was answered in.** A draft moves to the version asked now, filled in from its earlier answers by key. A final record keeps its version: an amendment corrects what was recorded, so it doesn't ask questions added later, and a record finalized before the center had questions gets none on its amend page.

**Staff only, unless a question says otherwise.** Staff who read the record (`records.view`) see every answer; front desk staff, who see only whether a record exists, see none. A director can mark a question "the student sees the answer", and the student then sees it with the summary on My writing. The student sees an answer only if its question was marked when the tutor answered and the latest published version still marks it, so marking a question later never shows students what a tutor wrote for staff. Each staff read of a record page or record form names the record's response in its `records.record_viewed` event. The FERPA export (format version 3) includes every answer, marked or not.

**Group copies get the answers.** Like the summary, next steps and topics. Each copy stays a draft for the tutor to read and finalize.

**Surveys are always anonymous.** The plan said anonymous by default. There is no setting for a named survey: its answers would be an education record with their own readers, export and audit, and no center has asked for one. The database refuses a survey response that has a student, appointment, record, person who answered or time (forms migration 0004), so adding named surveys later has to be a deliberate change.

**What a stored survey response keeps.** The form, the version, the center, the answers and the date in the center's time zone. Not the time. The invitation (`SurveyInvitation`) is never changed when its link is used, not even locked: a row lock would leave the answering transaction's ID on the invitation's row. The used link goes in `UsedSurveyToken` under a second hash of the token, which can't be matched to the invitation's hash without the link. The survey page writes no audit event, session or message, and doesn't look at who is signed in. `/survey/` is outside the staff two-factor gate, so a staff member who is also a student isn't redirected with the link in a query string.

**The token is never stored.** The scheduler writes the invitation and queues a task with its ID. The worker makes the token, stores its SHA-256 and sends the email through the delivery mailer directly, in one transaction. The queued mailer keeps each message's text in the task table, link included, and with the link anyone reading the database could find both the invitation and the used-link digest. If the relay refuses the email, the hash is rolled back and running the task again sends a new link. One consequence: survey emails need the task worker even when `SYMPRAXI_QUEUE_EMAIL` is off.

**What anonymity doesn't cover.** Someone with direct access to the database can see the order rows were written in (PostgreSQL's transaction IDs). Like the records' triggers, this doesn't stop whoever runs the database. Sympraxi's own pages and exports never show a single response, or a response with its date. For the reports still to come: don't list or export survey answers in row order or with their IDs.

**Survey links stay out of the logs.** Gunicorn's access log records each request with its time, and Django logs the path of every 404, so a used link opened again would land there too. With the database, either could match a response to its link. Both logs now write `/survey/[link]/` in place of the token, in the request line and the Referer header (`sympraxi/core/logs.py`; Gunicorn gets it through `--logger-class` in the Dockerfile). Turning the access log off would also have closed this, but it would leave an installation with no record of requests when something goes wrong. The CI smoke test opens a survey link on the real stack and fails if its token shows up in the `web` service's output. Caddy writes no access log in our Caddyfile; a campus that turns one on should scrub `/survey/` paths there too.

**Who gets a survey and when.** A center setting: when the tutor finalizes the student's record (the default), or from 30 minutes to a day after the appointment ends. Only students marked as here get one, so never for a canceled appointment, a no-show or a student who left a group. A student no one has marked gets none until they are marked, and finalizing a record marks them. Placeholders and meetings that weren't booked get none. The schedule's own survey goes out if it has one in use, otherwise the center's default. The scheduler looks back two days, so it catches up after an outage but never surveys a term of history after an upgrade. Students turn survey emails off under Account, Email reminders.

**Each invitation goes out once.** The invitation is unique per appointment and student and is written in the same transaction as its queued task, like reminders; a test races two sweeps. The link works once, for 14 days.

**Dead links look alike.** Unknown, used, expired, malformed, or for a survey that was stopped: the same 404 page, byte for byte apart from the CSP nonce. The URL inventory has a new "token" class for pages opened by a secret in the URL, with tests that a working token opens the page whether or not someone is signed in, and that every kind of dead token gets the same answer. Calendar feeds will use the same class.

**Results by term, from five responses.** Only directors see them (`forms.view_survey_results`). Answers are counted by question and option key across every version and shown in the latest wording; written answers are sorted, so their order says nothing about when they were given. A term shows nothing until at least five people have answered in it. The periods are terms, not any range of dates: a response counts in the latest term that started on or before the day it was given, so no two periods overlap and comparing them can't single out one response. Results aren't split by schedule or tutor. Responses don't record the tutor, because at a tutor with a few sessions a week the students would be easy to pick out. Reading results isn't audited, since no student can be identified from them; changing when surveys go out is.

## Phase 1: forms, intake and registration (October 2026)

**Questions and options have permanent keys.** A form's wording lives in numbered versions. Every question has a key that stays the same in every version, and so does every option of a choice question. Editing a published form starts a draft that copies it, keys and all, so moving a question, rewording it or rewording an option never changes what earlier answers mean. A question removed from a later version keeps its key in the versions that had it. WCONLINE stores answers by question number, which is why reordering or changing a question there scrambles past data.

**Answers are rows, stored by key.** A response is one person's answers to one version. Each answer is a row with the question's key, a typed value (text, a number, a date) and, for choices, the keys of the options chosen. Each answer also points to the exact question row it answered, so it is always shown with the wording the person saw, and the export lists both the words and the keys. The answers are rows, not one JSON document per response, because the reports still to come count answers by key and option key across every version, and because a database trigger can guard rows the way the records' triggers do. Questions skipped, or hidden because a condition wasn't met, have no row.

**A published version never changes, and answers are never edited.** A trigger (forms migration 0002) refuses any change to a published version, its questions or its options, and refuses adding to them. Publishing a draft is the last change a version takes. A response must answer a published version of its own form, and an answer must belong to a question in that version, under that question's key, choosing only that question's options. Responses and answers are append-only: changing answers means a new response, and the earlier one stays. A future retention purge will set `sympraxi.forms_purge`. As with the records' triggers, the database owner can still get around this.

**A question's kind of answer is fixed once it's published.** Until then a director can change it. After that, a short answer that became a date would mix two kinds of answers under one key, so the builder says to remove the question and add a new one, which gets a new key. A choice question needs at least two options with different wording. A yes or no question always offers Yes and No.

**One simple condition per question.** A follow-up shows only when one earlier choice question was answered with one of its options. It has to come after that question: the builder won't move it above, won't remove that question or option while the follow-up depends on it, and won't publish a version where the condition points anywhere else. Conditions refer to keys, so they carry over to new versions.

**Follow-ups work without JavaScript.** Each page carries a hidden list of the questions it showed. When the answers posted call for a follow-up the page didn't show, nothing is saved: the page comes back with the follow-up and says so (the "Continue" step). A Continue button does the same on purpose. With htmx, changing a choice that has follow-ups posts the form with `continue` set, and the questions are swapped in place; focus stays on the choice, and a status line says how many follow-ups appeared or went. An answer to a question that ends up hidden is dropped, so a response never holds an answer to a question the person didn't see.

**Directors reorder with buttons.** Each question in a draft has Move up and Move down buttons (WCAG 2.5.7, no dragging). Without JavaScript the page reloads with the question in its new place. With htmx the list is swapped in place, focus stays on the button, and a status line says what moved. At the top and bottom of the list the button stays focusable and is marked `aria-disabled`, so focus never falls off the page. Options are reordered with a Place menu on the question's page instead: move buttons inside that form would be the first submit button, so pressing Enter in a text field would move an option instead of saving.

**Registration is asked once, at the first booking.** A center has one registration form. A student who hasn't answered it sees its questions on the booking page, above the intake questions, and the booking and both sets of answers are saved together or not at all. A new version isn't asked again; students see and change their answers under "Your registration answers," and each change is a new response. Staff booking for a student aren't shown it.

**Intake: the schedule's own form, or the center's default.** A schedule with its own intake form in use asks it; every other schedule asks the center's default form. A form taken out of use isn't asked, and its answers are kept. Intake answers belong to the appointment, so they stay with it when it moves. In a group, each student answers for themselves and sees only their own answers. A weekly series booked by staff gets a copy of the answers on each appointment. Students can change their answers, as a new response, until the appointment starts.

**Staff can fill in the intake or skip it.** On the staff booking page every intake question can be left blank, which skips the form; answering any of them makes the required ones required again. A skipped form can be answered later by the student from the appointment page. Staff answers are recorded as theirs (`answered_by`), about the student.

**Demographic questions are always optional.** A question marked as asking about who the student is (for example gender, race or ethnicity, age, or first-generation status) can't be required; a check constraint in the database holds to that. Directors decide which questions those are.

**Who sees the answers.** Intake answers: the appointment's tutor, front desk staff and directors (`forms.view_intake`), on the appointment page and in the pre-session brief. Registration answers: directors see them all (`forms.view_all_registration`); tutors, for students they tutor, and front desk staff see only questions a director marked for staff (`forms.view_registration`). The current published version decides which questions those are, so unmarking a question hides the answers already given to it, and a question dropped from the form is seen by directors only. The question itself tells students when only directors see their answer. Students see all of their own answers (`forms.answer_own`). Every staff read is audited (`forms.answers_viewed`) with the student and the responses shown, never the answers; students reading their own aren't. Site administrators get none of these actions. Only directors build forms (`forms.manage`); adding a form, publishing a version and starting or stopping a form are audited.

**The FERPA export includes every answer.** Registration answers and each appointment's intake answers, earlier responses too, each in the wording of the version answered, with the option keys. The export format is now version 2.

**Room for the slices still to come.** The models already have the session-report and survey kinds, and a response's student is optional for anonymous surveys. The append-only trigger will need an exception for session-report answers on draft records, or each draft save can be a new response; locking them on final records can follow records migration 0002 (done in the next slice, above). Reports can count answers by `Answer.key` and by the option keys in `Answer.options`, across every version of a form. File-upload questions wait for the upload hardening planned for Phase 2.

## Phase 1: first-Monday load test (October 2026)

**The load test books through the real pages.** Virtual students and front desk workers open the schedules page, list open times, open the booking page and post its form over HTTP. The server uses the production settings without HTTPS and runs three web workers, as the Dockerfile's Gunicorn does, with the task worker and the scheduler beside them. Calling `services.book` in a loop would have skipped the work that costs the most, which is listing open times and drawing pages, and it couldn't show whether a refusal reaches the person as a message. Gunicorn doesn't run on Windows, so `tests/load/server.py` starts three processes that share one socket and each answer one request at a time, which is how Gunicorn's sync workers behave. Everyone starts signed in, with a session row each, so the run measures booking and not password hashing. `docs/development.md` says how to run it.

**The checks don't use the booking code.** `tests/load/check.py` reads the tables with SQL and works out each rule again: no tutor or student double-booked, no group over its size, no tutor cap or student limit exceeded, notice and horizon kept, every appointment inside its tutor's hours. Limits are replayed in booking order. A schedule whose limits count every schedule in the center can end the day over its limit with no booking breaking it, because a booking on another schedule is held only to that schedule's limits. The checker also compares the database with what each person saw: every appointment someone was shown as booked exists, and nobody holds one they weren't told about. Every refusal has to show a message. A server error, a dropped connection or a refusal without a message fails the run.

**Acceptable means a p95 under 1 second and a p99 under 2 seconds on every page.** Times are measured at the client, so waiting for a free worker counts. One second is the limit Jakob Nielsen gives for a response that doesn't interrupt the person's train of thought.

**Results on October 15, 2026.** Measured on a Windows 11 laptop with 8 logical processors and PostgreSQL 18.6 on the same machine, which was running other tests at times, at commit 9462a27 plus another session's uncommitted form-builder work (the seeded center has no booking questions). The standard run went twice: 500 students arriving over ten minutes, 150 of them in the first minute, while three front desk workers booked for students. Both passed. The first made 1,147 booking attempts (661 booked, 486 refused with a message) and the second 1,213 (656 booked, 557 refused), with no errors in either; 487 and 481 students got at least one appointment. There were no server errors or deadlocks, and every check passed. Every page's p95 was under 600 ms. Its p99 was under 800 ms in the first run and under 1.5 seconds in the second, which shared the processor with another session's browser tests. Nearly all the waiting came in the first minute, when requests averaged 56 a second (static files included) and the p95 across pages was 593 ms and then 808 ms. After that it stayed under 200 ms. Open times cost the most to draw: a day on the in-person schedule is about 98 KB of HTML, one row per tutor per time.

**Three workers ran the rush at about 90 percent of what they can serve here.** The same 500 students with no pauses between pages, arriving over two minutes, held three workers at about 62 requests a second, their limit on this machine. The median page then took 2 seconds, and Windows refused 168 connections once the listen backlog was full (behind Caddy they would probably have waited instead). The rush above averaged 56 a second in its first minute and reached 63 over ten seconds. With eight workers the same hard run passed, with every p95 under 250 ms. Static files were 42 percent of all requests, because each student's first visit loads the stylesheets, scripts and icons through the same workers. Proposed, not done: let an installation set the number of Gunicorn workers (the Dockerfile fixes it at 3) and document how to size it, and consider having Caddy serve `/static/` itself.

**The per-tutor locks cost nothing visible at this size.** PostgreSQL recorded no deadlocks in any run. Sampling `pg_stat_activity` two to five times a second, a query waiting on a row lock appeared in 3 of 4,409 samples across the two standard runs and in 7 of 563 in the hard run with eight workers, never more than one at a time. Most waited on a student's membership (one student, two requests); the rest waited on tutor assignments. The booking form's p50 was close to the open-times page's (84 ms and 81 ms). The lock order in "Row locks in a fixed order" stays as it is.

**Found and not fixed, because each changes what people see:**

- Open times still list tutors who have reached their daily or weekly cap, and the booking form then refuses with "This tutor is fully booked that day." That was 235 of the 486 refusals in the first run and 283 of 557 in the second, and some students got it on every try. Leaving those times out of the list wouldn't change the rule itself.
- A double-click books the time and then tells the student it failed. In every double-click where one request booked (34 in the first run, 31 in the second), the other was refused. In the first run that was "Someone else just booked that time." 21 times, "That time isn't open anymore." 8 times, and the student's own name followed by "already has an appointment then." 5 times. A browser shows the answer to the last click, so a student can be told the time is gone while holding it. The booking page could notice that the student already holds that time and show the appointment, and the button could turn off after the first click.
- All password sign-ins share one rate limit. allauth allows 30 sign-ins a minute from one address. Behind Caddy every request arrives from Caddy's address, and `ALLAUTH_TRUSTED_PROXY_COUNT` isn't set, so the 30 cover every student at once. A campus network behind one public address has the same effect. Of 150 password sign-ins in one minute, 30 got in and 120 got allauth's bare "Too Many Requests" page, since Sympraxi has no 429 template. Setting the proxy count to 1 when `SYMPRAXI_TRUST_X_FORWARDED_FOR` is on, raising the per-address limit and adding a 429 page would fix it. New accounts have their own limit of 20 sign-ups a minute per address, which should behave the same way (not tested). Single sign-on doesn't go through the sign-in limit.
- Limit messages say "the limit of 1 appointments a day", and front desk refusals start with the date even for a single booking.

## Phase 1: attendance, blocks and reminders (October 2026)

**Attendance belongs to each student, not to the appointment.** In a group, some students come and some don't, so attendance is kept on `Participant`: came, no-show, or not marked, with who marked it and when. The appointment keeps its two statuses ("Two statuses and three flags", below). A no-show still held the tutor's time, so its appointment stays scheduled and the overlap constraint needs no change. A late cancellation is an ordinary cancellation that frees the time, with `late_cancel` set on the student's row. Adding "completed" or "missed" statuses to the appointment would have had to say something about the whole group, and would have mixed what happened to the time with what happened to each student.

**A final session record means the student came.** Finalizing a record marks its student as here, and a student with a final record can't be marked a no-show. A record finalized after a no-show was confirmed overrides it, since the record shows the session happened. Records finalized before this slice were marked by records migration 0003.

**Possible no-shows are flagged, never decided.** Each schedule sets a grace period, 15 minutes by default. Each minute the scheduler flags any student no one has marked by then. A flag only asks staff to check: they confirm the no-show, mark the student as here, or clear the flag, and nothing counts until they do. Tentative appointments, placeholders, and students with any session record, even a draft, aren't flagged. The sweep looks back two days, so an upgrade doesn't flag a term of unmarked history; staff can still mark older appointments by hand. Tutors mark appointments they teach; front desk staff and directors mark any. A confirmed no-show sends the student a short email that says the session was recorded as missed, gives the count for the term, says what happens at the center's limit, and invites them to reply if they did come or something kept them away.

**Late cancellations are off until a schedule turns them on.** Each schedule sets a window, for example 120 minutes; a cancellation inside it is late. The window is separate from the change cutoff: with a 60-minute cutoff and a 120-minute window, a student can still cancel online between two hours and one hour before, and it's recorded as late. The cancel page warns them first. The student gets a late-cancellation email instead of the usual one. The tutor's email doesn't change. Staff canceling inside the window check "The student asked to cancel" when that's why; otherwise nothing is recorded, so a center never charges a student for its own cancellations. That box appears only for an appointment with one student, since one late cancellation can't belong to a whole group.

**Waivers keep the record and drop the count.** Front desk staff and directors waive a late cancellation or no-show with a reason. It stays on the student's record, and the export shows it with the reason, but it no longer counts toward a block. A waiver doesn't lift a block already in effect; that stays a director's decision. Like an exemption's note, the reason stays out of the audit log, which records who waived what and when.

**Blocks pause online booking, not the student.** A center sets limits that count every schedule; a schedule can set its own that count only that schedule and pause only that schedule. Each limit counts unwaived no-shows, or late cancellations, within the term of the appointment being counted, or from a date the director chooses. Counting is by the appointment's start, like the booking limits. When a no-show is confirmed or a late cancellation recorded, the check runs in the same transaction after the student's membership is locked, so two at once can't set two blocks or miss one (a test races two). A block ends after the last day of that term unless a director lifts it sooner. Lifting doesn't reset the count, so the next one past the limit sets a new block; to take one out of the count, staff waive it. While blocked, the student can't book for themselves, but their appointments stay and they can still cancel or move them; staff can book for them. The student sees why, when it ends, and whom to write to, on the booking pages and their appointments page. Setting and lifting are audited. Only directors see the list of blocks and lift them, because a block is a judgment about a student, like an exemption.

**Reminders are counted in real time and follow the appointment.** A schedule sets up to three reminders, from 30 minutes to 48 hours ahead; new schedules start with 24 hours and 1 hour. A reminder is due at the start minus its lead time in real hours, like notice and cutoff, so a day-before reminder across a daylight-saving change comes 24 hours ahead, which the clock reads as 23 or 25. The due time comes from the appointment's current start, so a moved appointment's reminders follow it, and the start time is part of what makes each reminder unique, so a moved appointment gets new ones. Canceled, tentative and placeholder appointments get none. A reminder that fell due before the appointment was booked, moved or confirmed is skipped, because the confirmation email just went out; so is a student's that fell due before they joined a group.

**Each reminder is sent once, enforced by the database.** The scheduler writes a `Reminder` row (appointment, recipient, lead time, start) and queues the email in the same transaction. A unique constraint on those four columns means a second scheduler, or a sweep run twice, inserts nothing and sends nothing; a test races two. The reminder also locks the appointment row, so a cancellation or move committing at that moment is seen. Reminders skip anything more than 15 minutes past due, so a scheduler that was down catches up on what is still close to on time and never sends a stack of stale ones. The shortest gap between two reminder choices is 30 minutes, so one sweep never sends two reminders for one appointment.

**Students opt out of reminders; tutors opt in.** The settings are on the account (Account, Email reminders), not per center, and every reminder links to them. A student's reminder names their tutor, the time and the place. A tutor's names no students; they sign in to see who it is. Reminders carry no calendar file, since the booking email already added the appointment.

**The scheduler is its own process.** `manage.py scheduler` sweeps at the start of every minute: reminders first, then possible no-shows. It runs as a fourth Compose service beside web, worker and db. The task worker runs jobs it is handed, and something still has to decide each minute which jobs are due; cron inside a container would need a second process manager. After each sweep that finishes without an error, the scheduler writes the time to a heartbeat file, and `python -m sympraxi.healthcheck scheduler` is healthy only if that time is under three minutes old. A scheduler that can't reach the database writes nothing and turns unhealthy, not only one whose process died. `upgrade.sh` stops it while migrations run and `restore.sh` while the database is replaced. Links in reminders need `SYMPRAXI_BASE_URL`; the production stack fills it in from `SYMPRAXI_DOMAIN`, and the command refuses to start without it.

**The row-lock order gains a level.** Memberships, then tutor assignments, then the appointment, then its participants. Marking attendance and canceling (when a student asked) now lock the students' memberships first, because either can set a block.

## Phase 1: session records (October 2026)

**One record per student, in groups too.** A session record is about one student. A group appointment gets a separate record for each student in it, so no student can see what was written about another. To save typing, the form for a group can start drafts for the rest of the group with the same summary, next steps, topics, length and resources. Staff notes and the writing project aren't copied, because notes are about one student and each student has their own projects. Every copy stays a draft until the tutor reads and finalizes it, and each student gets their own email. Students who left the group get no copy. The alternative, one shared record per group, would have meant either hiding the summary from students or showing each of them what was written about the others.

**Final records are locked in the database.** As with the audit log, a trigger (records migration 0002) does the locking. Once a record is final, an UPDATE of it, or any change to its topic tags or attached resources, is refused unless the same transaction has opened an amendment for that record. `services.amend()` writes the `Amendment` (author, time, reason, and each changed field before and after), sets `sympraxi.amendment` to its ID for the rest of the transaction, makes the change, and clears the setting. Even inside an amendment, the student, tutor, appointment and finalization can't change. Final records can't be deleted, and amendments are append-only. A future retention purge will set `sympraxi.records_purge`. Anyone with a database shell can set either value, so the trigger stops silent edits made through Sympraxi's code or the admin. Like the audit log's trigger, it doesn't stop the database owner.

**What finalizing needs.** A summary for the student, at least one concern tag, and a session that has started. Stages and tutor actions are optional. When a tutor finalizes an incomplete record from the form, it's saved as a draft and the page says what's missing, so nothing typed is lost.

**Who reads records.** Tutors read the records of students they have an appointment with in that center: past or upcoming, but not canceled, and not a group the student left. Upcoming appointments count so the pre-session brief works. Tutors also read the records they wrote. A record for a meeting that wasn't booked doesn't open the student's other records to its tutor; otherwise any tutor could reach a student's history by starting a draft about them. Tutors edit and amend only their own records. Directors read, write and amend every record in their center, and only directors export. Front desk staff see whether a record is final, a draft or not written (on the appointment page, the day sheet and the records-to-write list), never what it says. Site administrators get none of these actions. A student sees only their own final records, and only the parts written for them. As with appointments, someone else's record is a 404 for people who can see some records, so record IDs can't be probed. The build plan lets directors widen or narrow tutors' access per center; that setting isn't built yet.

**Pages about a student use the student's membership.** The history, brief and export are about one student in one center, and the student's `Membership` holds both. Their URLs use the membership's UUID, so no name or student ID appears in a URL, and the policy gets one object that knows both the student and the center.

**Every staff read is audited.** Opening a record or its form, opening a student's history, and each pre-session brief shown on an appointment page write `records.record_viewed` or `records.history_viewed`, with the student's ID and which page it was. Saving, finalizing, amending (with the names of the fields changed), exporting and changing the settings are audited too. No event holds record text. Students reading their own records aren't logged, since that isn't a disclosure.

**Students see summaries, next steps and resources.** `Center.students_see_staff_notes`, off by default, adds the staff notes to the student's My writing page. Either way, the record form tells tutors that students can ask to see everything written there (34 CFR 99.10), and My writing tells students they can ask for a copy. Topic tags aren't shown to students; they're in the export. When a final record is amended, My writing shows the date it was updated but not the earlier text.

**The summary email says it's ready and links to it.** It names the tutor, the center and the date. `Center.summary_email_includes_text`, off by default, adds the summary and next steps. Staff notes never go in an email. The email goes through the queued mailer after the transaction commits, so a rolled-back finalize sends nothing. Amendments don't send another email.

**The FERPA export.** A director can export one student's complete record in their center, as JSON or as a page to print or save as PDF: account details, every appointment (canceled ones and groups the student left included), every session record (drafts included) with staff notes and each amendment's before and after, attached resources with the tutor's notes and each resource's license, and writing projects. Other students are left out (99.12): a group appointment shows how many students it had, never who. Each export is audited. The disclosure log (99.32) comes in a later slice.

**The catalog is loaded by a command.** `manage.py load_catalog` reads `catalog/vocabulary.yaml` and `catalog/resources/*.yaml` and matches on topic slugs and resource IDs, so a second run changes nothing and an edited entry is updated in place. Nothing is deleted. A resource that leaves the catalog is marked inactive, because records may still point to it, and a topic missing from the file is reported. One bad entry stops the whole load. Each resource keeps its license, publisher and (for OpenStax) the CC BY source it can be copied from. The catalog changes between releases without any change to the schema, so `install.sh` and `upgrade.sh` run the command every time, and so does `seed_demo`. The Docker image now includes `catalog/`. It needs PyYAML, the one new dependency.

**Topics and resources live in the records app for now.** The build plan's layout gives resources an app of their own. Today every use of a resource goes through a session record, so the two models share `sympraxi/records`; moving them out later is a matter of two models and their loader.

**Centers add links, not files.** Directors add their center's own resources: a title, an https address, their own summary, publisher, license and topics. Those links are offered only in that center and come first when a suggestion ties. File uploads wait for the upload hardening planned for Phase 2.

**Suggestions follow the concerns.** A resource scores 3 for each concern it shares with the record. One that shares none scores 2 if it has a more specific term under one of the record's concerns (record: `citation`, resource: `citation:apa`), or else 1 if it has a related term (the parent, or another term under the same parent). Related terms don't add to a shared one, so a page tagged both APA and MLA doesn't outrank an APA page on an APA record. Each matching stage or action adds 1, but a resource needs a concern point to be suggested at all, because nearly every resource fits "drafting" or "revising." The top eight show.

**The record form works without JavaScript.** Attach and Search are submit buttons in the form. Without htmx they post the form back and redraw it, unsaved and without error messages. With htmx, checking a topic refreshes the suggestions, the search updates as the tutor types, and Attach adds the resource in place; each request sends only the fields it needs (`hx-params`), so the notes never travel with a search. A status line announces what changed. Resource links on the form open in a new tab and say so, so following one doesn't lose an unsaved record. Concern terms are grouped under their parents in `<details>` elements, which work by keyboard with no script.

**Writing projects are basic.** Tutors start a project from the record form, and the tutor or a director can edit it or mark it finished. Students can't add or edit their own projects yet.

**Records stay out of the Django admin.** The admin is for site administrators, who have no access to records, so none of the records models are registered there.

## Phase 1: single sign-on (October 2026)

**One Entra tenant and one Google domain per installation, set in the environment.** The build plan had each center entering its own tenant's settings. An installation serves one college, though, and a college has one tenant or one Workspace domain. Reading providers from `SYMPRAXI_ENTRA_*` and `SYMPRAXI_GOOGLE_*` variables keeps client secrets out of the database and its backups. allauth's admin screens for apps and tokens are removed, and an app saved in the database is ignored. A provider with only some of its variables set stops the site from starting, rather than quietly leaving SSO off.

**allauth's generic OpenID Connect provider for both.** allauth's Microsoft provider reads the Graph profile, whose `mail` field isn't verified and which carries no tenant or `amr` claim. The generic provider reads the ID token, which has everything the checks need. Userinfo isn't fetched, PKCE is on, and tokens aren't stored. The sign-in URLs are `/accounts/oidc/entra/...` and `/accounts/oidc/google/...`.

**The tenant is pinned three ways.** The discovery document is the tenant's own (`/{tenant}/v2.0`), so allauth rejects ID tokens from any other issuer. `common`, `organizations`, `consumers` and anything that isn't a GUID are refused at startup. `sympraxi/accounts/sso.py` also checks `tid` and `iss` on every sign-in.

**Only addresses the provider vouches for.** Entra's `email` claim is unverified and editable, the hole behind the 2023 "nOAuth" account takeovers. Sympraxi requires Entra's `xms_edov` claim (the address is in a domain the tenant verified), and Google's `email_verified` plus a matching `hd`. When `SYMPRAXI_SIGNUP_EMAIL_DOMAINS` is set, the address must be in it. The checks run on every sign-in, so an account that stops passing them can't keep using SSO.

**Linking by address, with two limits.** A sign-in that passes the checks is linked to an existing account with the same address. After that, sign-ins match the provider's subject ID, so a later change of address doesn't break the link. An account already linked to a different identity at the same provider is never linked again by address: colleges reuse addresses, and a new holder must not inherit the old holder's records. allauth removes the password of a matched account whose address was never verified, so whoever registered it first loses access. Links, unlinks and refused sign-ins are audited (`auth.sso_linked`, `auth.sso_unlinked`, `auth.login_failed` with a reason).

**SSO doesn't skip the staff 2FA rule unless the token proves MFA.** By default allauth's two-factor step runs after SSO like after a password, and staff without a second factor are sent to set one up. `SYMPRAXI_TRUST_IDP_MFA` accepts the provider's MFA only when the ID token's `amr` claim contains `mfa`. Nothing else counts, including Google's `hwk` and `swk`, whose meaning as multi-factor Google doesn't define. Entra sends `amr` once it is added as an optional claim. Google began sending `amr` in June 2026, on request, and only to apps it has verified, so an Internal Workspace app may never receive it; those installations keep Sympraxi's own 2FA.

**SSO-only is enforced at sign-in, not in the template.** `SYMPRAXI_SSO_ONLY` hides the password form, passkey button and sign-up link. `AccountAdapter.pre_login()` refuses every non-SSO sign-in except a site administrator's, from any page. Site administrators keep a break-glass password page at `/accounts/login/local/`, with two-factor login as usual. Without a provider, the setting is refused at startup and ignored at runtime, so it can't lock everyone out.

**SSO buttons are forms, and form-action allows the provider.** Starting sign-in takes a POST, so a link on another site can't start one. Browsers apply the Content Security Policy's `form-action` to the redirect that follows a form, so the policy adds `https://login.microsoftonline.com` or `https://accounts.google.com`, only for providers that are set up. A browser test presses each button from the keyboard and checks that the browser then requests the provider's page, which it does only if the policy allows the redirect. The test browser resolves no host but localhost, so that request, like any other a page might make, never leaves the machine. Playwright can't intercept a request made while following a redirect, so blocking name lookups is the only dependable guard.

**Plain text buttons, no logos.** "Sign in with Microsoft" and "Sign in with Google" use the standard USWDS button. Vendor logos would put trademarked artwork in the repository for no gain in clarity.

## Phase 1: scheduling core (October 2026)

**No double-booking, enforced by PostgreSQL.** An exclusion constraint (`scheduling_appointment_no_tutor_overlap`) rejects two active appointments for the same tutor whose times overlap, on any schedule in any center. The `=` on the tutor column needs the `btree_gist` extension, which the first scheduling migration creates. It is a trusted extension, so the database owner can create it without superuser rights. The booking service checks first so people get a readable message; the constraint catches the race that check can't.

**The break after an appointment is stored on the row.** Each appointment keeps `blocked_until`, its end plus the schedule's buffer at booking time, and the constraint covers `[starts_at, blocked_until)`. The constraint can't add the buffer itself: adding an interval to a `timestamptz` isn't an immutable expression, so PostgreSQL won't index it. Changing a schedule's buffer later leaves existing appointments as they are.

**Row locks in a fixed order.** Booking, changing and canceling each run in one transaction and lock rows in the same order: the students' memberships (their limits and their own calendars), then the tutor assignments by primary key (caps and group seats), then the appointment. Two students racing for the last seat in a group, or one student booking twice at once, can't both get through. The locks use `select_for_update(of=("self",))`, so joined rows such as the center stay unlocked and bookings across a center don't queue behind each other. A booking or a move locks every assignment its tutor has, on every schedule, not only the one being booked. With only that one locked, two students booking one tutor on two schedules at the same moment could both insert, and PostgreSQL stopped one with a deadlock while checking the exclusion constraint; that student got a server error. Now the second booking waits for the first to commit, sees it and is refused. Bookings for one tutor queue even when their times don't overlap, but each holds the locks only for its own short transaction. The constraint stays as the backstop: if it, a deadlock or a serialization failure still stops a booking or a move, the person is told the time was just taken.

**Wall-clock times on daylight-saving nights.** Weekly hours and opening hours are wall-clock times in the center's zone. A wall-clock time stands for the first instant at which the clock reads that time or later. On the night clocks go back, 1:30 means the first 1:30; on the night they go forward, 2:30 means 3:00. Slots step in real time from the opening instant, so the repeated hour gets its own slots and every appointment lasts as long as it says. A weekly series keeps its wall-clock time each week. Notice, horizon and cutoff are measured in real time.

**Limits count by the appointment's start, in local time.** A day is a local calendar day (23 or 25 hours on switch days), a week runs Monday to Sunday, and a term is the schedule's term dates. Canceled appointments and placeholders don't count. When "count appointments on every schedule" is checked, a schedule's limits count the student's appointments on all of the center's schedules; each schedule's own limits apply when booking on it.

**Exemptions cover appointments, not booking days.** An exemption lifts a student's count and minute limits for appointments on or before its last date, so the last day of an exemption can't be used to book a month ahead. Notice, horizon and cutoff still apply. Every exemption has an end date. Adding or ending one is audited, without the note.

**Staff book under different rules.** Front desk and directors aren't held to minimum notice, the horizon or the change cutoff, so they can enter walk-ins and fix mistakes. They are held to student limits and tutor caps unless they check "book even if it goes over," which the audit log records. Nobody can book outside a tutor's hours or over another appointment.

**Students move their own one-to-one appointments; staff move groups.** Until the change cutoff, a student who is the only person in an appointment can move it to another open time on the same schedule. The move keeps the appointment's row and calendar UID, raises its `SEQUENCE`, and re-checks every booking rule while leaving the appointment itself out of the counts. Moving to another schedule means canceling and booking again. Only staff move group appointments, because a move changes the time for everyone in the group. Moving has its own policy action, `scheduling.change_appointment`, granted like canceling.

**Grants that reach only a person's own records.** Students can view, cancel and move only the appointments they are in, and tutors can view only the appointments they teach. These limits are `OBJECT_RULES` in `policy.py`, beside the role grants, and `tests/test_policy_matrix.py` lists them by hand. Someone else's appointment returns 404, as it does for an outsider, so appointment IDs can't be probed. Students never see other students: open times carry no names, and only staff and the tutor see who is in a group.

**Site administrators get no scheduling actions.** Appointments are student records, so the Phase 0 rule holds: they are reached through a center role, not through `is_superuser`.

**Two statuses and three flags.** An appointment is scheduled or canceled. Walk-in, placeholder and tentative are flags on a scheduled appointment, and a tentative booking holds its time until staff confirm or cancel it. The constraint ignores only canceled appointments, so a status added later that still holds the time (completed, missed) is covered without a migration.

**Extra hours stay inside opening hours.** A tutor's extra hours can add time on a day they don't usually work, but never past the schedule's opening hours. A center that stays open late for finals changes the schedule's hours.

**Appointment emails say as little as possible.** A student's email names their tutor, the time and the place. A tutor's email says a student booked and links to the appointment, without the student's name. Mail goes out after the transaction commits, so a booking that is rolled back sends nothing. `SYMPRAXI_BASE_URL` sets the links in mail sent outside a page request, such as the reminders still to come.

**Calendar files are written by hand.** An appointment needs about a dozen iCalendar properties, and the rules that matter (escaping, CRLF line endings, folding at 75 octets) fit in one short module, so there is no `icalendar` dependency. Each appointment keeps one UID. Bookings and changes go out as `METHOD:PUBLISH` with a rising `SEQUENCE`, cancellations as `METHOD:CANCEL`. Calendar apps vary in how they handle these, so the email text is the record. The queued mailer now carries attachments, as text or as base64 for binary files.

**Property-based tests with Hypothesis.** A state machine books, cancels and moves appointments at random on two schedules that share a tutor, across a daylight-saving week, and checks the tables after every step: no tutor or student is double-booked and no limit, cap or group size is exceeded. The checks are computed independently of the booking code. The default run plays the same sequences every time, so CI is repeatable, and it fails if those sequences never book, cancel, move or reach a limit, so it can't pass by being refused everything. `HYPOTHESIS_PROFILE=thorough` plays about twelve times as many, chosen at random. A separate test races real threads in committed transactions.

**PostgreSQL 18 for local tests on Windows.** The pgserver package's PostgreSQL has no contrib extensions, so it can't create `btree_gist`. The local runs for this phase used the EDB PostgreSQL 18.6 binaries zip, started from a scratch folder on its own port. The `postgres` Docker images and the Debian and Ubuntu packages include `btree_gist`.

## Phase 0 (October 2026)

**Django 6.1 now, Django 6.2 LTS before the pilot.** The build plan first said "5.2 LTS now." Moving from 5.2 to 6.2 crosses a major version. Moving from 6.1 to 6.2 is a single feature release, and 6.2 LTS ships in April 2027, before the summer pilot. Django 6.x also brings two things Sympraxi would otherwise need packages for: a built-in Content Security Policy with nonces, and the Tasks framework. Renovate is set not to jump to 6.2 automatically.

**Background jobs: Django's Tasks framework with the `django-tasks-db` backend.** Jobs are stored in PostgreSQL and run by `manage.py db_worker`, so a small install needs no Redis or Valkey. The jobs are written against `django.tasks`, so a different backend can be swapped in later without code changes.

**Email through `MAILERS` (new in Django 6.1).** The `default` mailer hands messages to the task worker. The `delivery` mailer talks to the campus SMTP relay. A slow relay never holds up a page.

**Shared cache in the database.** Login rate limiting needs a cache that all Gunicorn workers share. Django's database cache does that without another service. Set `CACHE_URL` to a Valkey URL if a large install needs it.

**Design system: U.S. Web Design System 3.14.** It is built and tested for accessibility, and its code is in the public domain (CC0); its fonts are under the SIL Open Font License and its icons under Apache 2.0. We use its components and styles but not the U.S. government banner or anything that implies a government site. GOV.UK Frontend was the alternative; its typeface and crown are restricted to UK government services.

**Assets are copied from npm packages, not loaded from a CDN.** A self-hosted install makes no third-party requests, which keeps the Content Security Policy at `'self'` and keeps students' browsing private.

**Server-rendered pages with htmx.** Less JavaScript, fewer accessibility traps, a smaller attack surface. htmx is configured with `allowEval` and `allowScriptTags` off and without its inline indicator styles, so it works under the strict CSP.

**Permissions in one module.** `sympraxi/core/policy.py` holds every rule. A hand-written test matrix and a URL inventory test keep it honest. Outsiders get 404 rather than 403, so URLs can't be used to discover which centers or records exist.

**Site administrators are not a back door to records.** Superusers get operational actions only (`SITE_ADMIN_GRANTS`). Actions that read student records will be granted by center role, never to site admins by default.

**The audit log is append-only in the database.** A PostgreSQL trigger rejects `UPDATE` and `DELETE` on `privacy_auditevent`. A future retention purge will set `SET LOCAL sympraxi.audit_purge = 'on'` for its own transaction. The actor and center are stored as IDs without foreign-key constraints, plus a text label, so deleting a person or center never rewrites history.

**Two-factor login required for every staff role.** Tutors, front desk, directors and site admins are sent to the 2FA setup page until they add an authenticator app or a passkey. Text-message codes are not offered. The Django admin uses the same sign-in, so the same rule applies there.

**Python 3.12 in Docker and CI**, matching development machines. Security support for 3.12 runs to October 2028.

**PostgreSQL 18 in production and CI.** The local test run on Windows used a portable PostgreSQL 16 because Docker wasn't available. Nothing in Phase 0 depends on 18.
