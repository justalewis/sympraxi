# Technical decisions

Short records of choices made while building, with the reason, so later contributors don't have to guess. Newest first.

## Phase 4: the finished time clock (October 2026)

**Networks.** A center can list the networks staff may clock in and out from (one address or range per line, IPv4 or IPv6). Staff outside them are refused with a message that points them to a director, and the refusal is logged. Directors and site administrators are exempt, and a director can still add time for anyone from anywhere, so the rule stops a tutor clocking in from home, not a director fixing a missed shift. It trusts the address Sympraxi sees, which is the proxy's last forwarded address when the host has said it trusts one (`SYMPRAXI_TRUST_X_FORWARDED_FOR`); a host that gets that wrong will see everyone as outside or inside together.

**Approval and locking.** A director approves one person's hours for a run of past days. Approval needs the last day to have passed, no open entry, and no entry that was closed at midnight and not yet checked. While it stands, entries that started on those days can't be added, changed or removed, by anyone, until the approval is withdrawn with a reason. Approvals can't overlap (the database enforces it), and a withdrawn approval stays in the table, so a payroll question months later can be answered.

**What payroll gets.** The timesheet download now has a payroll ID and pay code per person (entered on the time clock settings page) and an Approved column (Yes, Partly, No) on both tables, and it can be limited to approved hours. Nothing is sent to a payroll system; the file is the handoff.

**Not done.** Approval is per person and period, not a pay-period calendar with a single approve-everyone button. A person can't see whether their hours are approved on their own page. Clock-in network rules don't apply to the kiosk yet, which doesn't exist until the next slice.

## Phase 5: launch from a learning management system (October 2026)

**LTI 1.3 launch only.** A student or instructor clicks the writing center in their Canvas, Moodle or D2L course and arrives signed in. Sympraxi answers the platform's third-party login, then checks the signed `id_token` against the platform's published keys (RS256 only), plus the issuer, audience, deployment ID, expiry, message type and a one-time nonce. The nonce is stored and used up on arrival, so a captured launch can't be replayed. The state is signed instead of kept in the session, because the platform's post comes from another site and browsers don't send session cookies with it.

**Who is trusted.** A platform's word about who someone is signs them in, so only a site administrator registers one (in the admin), tied to one center. The email must be at one of `SYMPRAXI_SIGNUP_EMAIL_DOMAINS`; the first launch ties the platform's identifier for the person to the account with that email, and later launches match on the identifier. The platform's role claims are ignored: a launch makes someone a student of the center if they have no role there, and never gives staff access. Staff still meet two-factor.

**Not done.** No deep linking, no grade passback, no names-and-roles service, so the tool needs no keys of its own. Canvas lets a tool open in a new window; the site refuses to be framed, so set the placement to open in a new tab. This has been tested against a stand-in platform, not a real Canvas, Moodle or D2L.

## Phase 5: more ways to sign in (October 2026)

**A generic OpenID Connect provider.** Besides Microsoft Entra and Google, a college can point Sympraxi at any OpenID Connect provider (Okta, Keycloak, Shibboleth's OIDC add-on and others) with an issuer address, a client ID and a secret. It uses PKCE, and checks the issuer, that the provider says the email is verified, and that the address is at one of `SYMPRAXI_SIGNUP_EMAIL_DOMAINS`. That list is required for this provider, because unlike Entra's tenant or Google's hosted domain, a generic provider doesn't say which people belong to the college.

**CAS.** A college that runs a CAS server (2.0 or 3.0) can sign people in through it. The person is sent to CAS and comes back with a one-time ticket; Sympraxi asks the CAS server, from its own server and over https, who the ticket is for. The XML answer is refused if it declares a DTD or entity. CAS has no "email verified", so the address must come from an attribute (or the CAS name) and be at an allowed domain. The first sign-in ties the CAS name to the account with that email; later sign-ins match on the CAS name, so an address handed to a new person doesn't hand over the old person's records. Two-factor, the sign-in audit and SSO-only mode apply as with the other providers.

**Student ID from the provider.** A host can name the claim (`SYMPRAXI_SSO_STUDENT_ID_CLAIM`) or CAS attribute that carries the college's student ID. It fills a blank student ID, never overwrites one, and records a mismatch (or a clash with another account) in the audit log instead of changing anything.

**Not done.** SAML needs a new library with native XML-signature code, so it waits for approval to add one. Colleges on Shibboleth can use its OIDC add-on or CAS in the meantime.

## Phase 5: text message reminders (October 2026)

**Consent comes first.** A person gives a mobile number and ticks a box that is never pre-ticked. Beside it is the exact wording they agree to (who texts, why, how often, that message and data rates may apply, and how to stop). That wording, its version, the time and the address they agreed from are stored. They then prove the number is theirs with a six-digit code texted to it (good for 15 minutes, five tries, one new code a minute). Only after that can they be texted a reminder. Agreeing is not a condition of using the center, and the wording says so.

**Stopping.** A person turns texts off on their account page, or replies STOP (also UNSUBSCRIBE, CANCEL, END, QUIT, STOPALL) to any text, which turns off every consent on that number. HELP gets a short reply. START and YES do not turn texts back on: a person who stopped has to turn them on again on the site, where they see the wording. If the carrier says a number can't be texted, the consent ends and the reason is recorded.

**What is sent.** Only appointment reminders and the confirmation code. A reminder carries the site's name, the center's name and the time, and no person's name, tutor or topic. It goes only for the last reminder a schedule sends before an appointment, so a person who chose texts isn't sent one for each email, and never between 9 pm and 8 am in the center's time zone (a reminder that falls then is recorded as not sent, not delayed). A director turns it on for the center, and the host must have set a provider.

**Providers.** A small interface with two providers, both using only the standard library: `console` (writes each text to the log, for trying the flow) and `twilio` (Twilio's messages API, with replies checked against Twilio's signature). Email-to-SMS gateways are not used. The phone number is encrypted with the site's secret key and kept with a keyed hash, so an incoming STOP can find it. A message's words are deleted once it has been sent; the record of what was sent, when and whether it worked stays.

**Not done.** Numbers outside North America must be typed with a + and a country code, and numbers aren't checked for being mobile before the first send (the carrier's answer is). No other providers, no texts from the center to a group, no two-way conversations, and no per-center sender number.

## Phase 5: early alerts and shared visits (October 2026)

**An alert needs a reason.** A tutor (for students they have tutored), a front desk person (any student) or a director raises an alert by choosing what it is about (stopped coming, disengaged, a well-being concern, or something else) and writing why, in at least 15 characters. The database also refuses an alert with no reason, and refuses to close one with no outcome. The form asks whether the student knows, and records the answer either way; it does not require telling them, since there are cases where staff shouldn't, but it makes the choice visible later.

**Who reads it.** Directors read and handle every alert (acknowledge it, then close it with a note on what was done). The person who raised it reads their own. Nobody else does: not other tutors, not the front desk, not the student's instructors, and not site administrators. The email that tells the directors (or a single center-set address) names the student and the kind of alert and links to the page; the reason is never in an email.

**What the student can see.** Under the data export a student can ask for, an alert appears as its date, its kind, whether they were told, and its status; the staff member's words and the closing note are left out. If a center believes a student has a right to those words, a director can read them with the student. This is a judgment about where a staff member's candid note and a student's right to inspect their record meet, and a campus's records office should confirm it.

**Shared visits.** A center can turn on letting students send an instructor a confirmation of a visit (off by default). After the visit has happened, the student enters the instructor's email, and the instructor gets a link that opens without an account. It shows the student's name, the day, how long the appointment was, and either "staff confirmed that they came" or "not marked as attended, so it isn't confirmed yet." It says nothing about the topic, the tutor, or any note. The link lasts 120 days and the student can turn it off. Only a hash of the link is stored, and a dead link looks the same as one that never existed. Nothing flows the other way: instructors can't ask about students.

**Not done.** No alert categories set per center, no assigning an alert to a particular person, no reminder when one sits open, no alert from a student's own report of a concern, and no way for an instructor to be told when a student has stopped visiting (on purpose).

## Phase 5: the API and webhooks (October 2026)

**Tokens.** A director makes a token for the center and chooses scopes from five: read schedules, read appointments (with the students in them), write appointments (book and cancel), read students, read workshops. The token is shown once and only its SHA-256 is kept. It acts as the director who made it, so a token can never do more than that director can, and it stops working if they lose the role or the account is turned off. Tokens expire (30, 90 or 365 days, or never), can be revoked, and are limited to 600 calls a minute. The limit is counted in the shared cache, so it is per token across all the web workers.

**Writes.** Booking and canceling go through the same service functions as the website, so limits, booking blocks, hours and the double-booking rule hold. They are audited as made by the token (`API token sym_...`) on behalf of the director. The API can't touch session records, notes, files or anything written about a student's work: those have no scope.

**Webhooks.** Six events, driven by the audit log so there is one place that decides what counts as something happening. A notice carries ids and times only, never a name, email or note; a receiver asks the API for details with its own token. Notices are signed with HMAC-SHA256 over the timestamp and body (the secret is stored encrypted with the site key and shown once), sent by the task worker, retried on a backoff and then given up on. Addresses must be https and public: the host name is resolved and refused if any address is private, loopback or link-local, which stops a webhook being aimed at the host's own network. `SYMPRAXI_WEBHOOKS_ALLOW_PRIVATE` turns that off for development.

**Not done.** No per-scope rate limits, no IP allow-list on tokens, no write access to people, schedules or workshops, no webhook for record events (on purpose), and no replay button for a failed notice.

## Phase 4: cohorts, mentors, observations and finishing onboarding (October 2026)

**Cohorts and mentors.** A director starts a cohort (a group of new tutors or front desk staff), adds people to it, and gives each a mentor, who can be any tutor, front desk person or director other than the person themselves. Mentors see the people they mentor on their own page; a director sees everyone's.

**Sign-off.** A mentor or director signs off a module only after the person has finished every item in it. The sign-off names who signed and when, and may carry a short note.

**Observations.** A director writes checklists: a list of things to look for. An observer (the mentor, or a director) starts an observation of a tutor from a checklist, rates each item from needs work to strong, adds comments, and submits it. Until then it is a draft only the observer sees. A submitted observation is locked, including by the database (a trigger refuses any change or deletion of it or its ratings), and the observed tutor can read it. A checklist item that has been used in an observation can't be deleted.

**Why not the form builder.** The build plan said observation forms would use the form builder. The form builder's responses belong to a student and an appointment, and its reports, exports and retention rules assume that, so an observation of a tutor would have had to be forced into a student's record or the builder reworked. A small checklist of rated items does the job and keeps tutors' observations out of every student export. If you want free-text observation forms with different question types later, that is a separate piece of work.

**Finishing.** A person has finished onboarding when every required published module is done and signed off, they have at least the cohort's number of submitted observations, and they have the center's training hours. Then a director marks it complete, which records who and when. Nothing completes itself. The cohort page shows each person's position on all four.

**Not done.** No reminders to mentors or tutors who are behind, no email when an observation is submitted, a person can't be moved between cohorts (remove and add), and observations are not yet part of a tutor's own data export, only the center's.

## Phase 4: tutor training modules (October 2026)

**What a module is.** A director builds modules out of three kinds of item: a page of text, a reading or video elsewhere (opened in a new tab, with a note), and a short quiz. A module is a draft until it is published, and tutors and front desk staff see only published ones. A page or link counts as done when the person marks it; a quiz counts when they pass it, with the passing score set per quiz, and they may retake it as often as they like. A module is complete when every item is done, which is logged. A new app, `training`, holds all of it.

**Quizzes.** One right answer per question, two to five answers, scored on the server. A failed try says which questions to look at again and never shows the right answers, so retaking is a real check. Every try is kept (the score and what was chosen).

**Hours.** The requirement is one number on the training page (hours of training a new tutor completes), and the hours themselves are the time clock's Training category, not a second timer. Open and removed entries don't count.

**Progress.** Directors see a table of every tutor and front desk person against every published module, their training hours, and whether onboarding is complete (every required module done and the hours met).

**Not done.** Deleting an item deletes its completions, so a director who removes a page erases the record that someone read it; unpublish instead. Items can't be edited into a different kind, and a quiz can't be reordered within a module except by moving the quiz item. No training for students, no certificates, no deadlines or reminders, and no per-cohort view yet (the last slice adds cohorts).

## Phase 4: workshops (October 2026)

**What a workshop is.** A session for a group, separate from the one-to-one schedules: a title, a day and time in the center's zone, where, an optional meeting link, a leader, an optional number of seats, and a status of draft, published or canceled. Nothing about a workshop touches tutors' schedules, booking limits or no-show blocks. A new app, `workshops`, holds it so the scheduling code stays about appointments.

**Who does what.** Directors create, change and cancel workshops. Students see published ones and register until the start; the registration emails them the details, and they can cancel until it starts. A seat is counted with the workshop locked, so the last one can't be taken twice. The leader (a tutor, front desk person or director) and the front desk can run the roster: mark each student came or did not come once it starts, add a student at the door by email or student ID, remove one, and download the roster as CSV, which is logged because it names students. Canceling a published workshop emails everyone registered; canceling a draft tells no one.

**Records.** A student's own export now carries their workshop registrations and attendance (and, in the same change, their waiting-list requests and front desk check-ins: version 9), and the center's export carries workshops, registrations, arrivals, timesheet approvals, payroll details and the waiting list.

**Not done.** No waiting list for a full workshop, no reminder email the day before, no recurring workshops, and no workshop attendance in the statistics reports or on a student's timeline. A student who registered can't be moved to another workshop; they cancel and register again.

## Phase 4: the waiting list (October 2026)

**What a student asks for.** A student on a schedule that has a waiting list turned on says which day they could come, the window within it, how long, how they would meet, and optionally which tutor. One request per student per day per schedule, and no more than five open at once. This is a wish, not a place in a queue for one particular full time, because a full time is never listed anywhere a student could pick it.

**What happens when a time opens.** When an appointment is canceled or moved away, the oldest waiting student whose wish fits is considered first. Before offering, Sympraxi tries the student's booking and rolls it back, so a student who has hit a limit or a booking block is skipped without losing a hold on them. The time is then held as a placeholder appointment for the schedule's hold length (15 minutes unless the director changes it); the overlap rule in the database keeps everyone else out of it, and the student gets an email with a link. Accepting cancels the hold and books the student in one transaction under the usual rules, except that minimum notice and how far ahead one may book are waived, since the time just opened. Declining, leaving the list, or letting the hold run out offers the time to the next student. If the freed time was longer than the student needed, the rest goes to the next person on the list.

**What the front desk sees.** A list of everyone waiting across the center's schedules, with each person's status and a Remove button.

**Not done.** The list takes no account of a student's priority (a student with few visits does not go ahead of one with many). A student is not told how many are ahead of them. A hold lapses on the scheduler's once-a-minute sweep, so it can run a minute past its stated end, and if the scheduler is stopped nothing expires until it is back. Group appointments with a free seat do not trigger offers; only a whole appointment freed does.

## Phase 4: the check-in kiosk and waiting room (October 2026)

**The kiosk.** A page for a shared screen, kept signed in by a front desk person or a director. A student types their ID, or swipes a card through a reader that types the number and presses Enter (a magnetic stripe's track data like `;123456789?` is read too), and the page says only their first name and whether they are checked in, then returns to the start after eight seconds. An unknown ID gets the same wording whether the ID doesn't exist, belongs to staff, or belongs to another center, so the kiosk can't be used to find out who is who. If a center has listed its networks for the time clock, the kiosk uses the same list and refuses check-ins from outside it.

**What check-in does.** A student with an appointment under way or starting within 30 minutes is checked in for it; otherwise they are a walk-in and can say what they're working on. Checking in twice changes nothing, and the database allows one waiting arrival per student. A student who checked in is never flagged as a possible no-show for that appointment, because someone saw them walk in. Attendance itself is still marked by staff.

**The waiting room.** Front desk, tutors and directors see who is waiting, longest wait first, with the appointment or the walk-in note, and mark each student seen or gone. Front desk and directors can also check a student in by ID from the same page. The page lists today's seen and gone students with how long each waited.

**Not done.** The kiosk has no lock against someone trying many IDs in a row; it relies on the device being at the front desk and the audit log. There is no sound or screen notice to tutors when a student arrives, and arrivals aren't yet in the reports (average wait, walk-ins per day). A card reader that sends something other than an ID in the track data needs a format added to `parse_card`.

## Phase 3: history import (October 2026)

**What it is for.** A center moving from WCONLINE keeps its past: how often each student came, who no-showed, how many sessions a tutor ran. Without an import the new system starts empty and the no-show rules and visit counts start from zero. It is not required to run Sympraxi; a new center, or one willing to start fresh, never needs it.

**What was built, because you can't get WCONLINE exports.** A generic CSV importer, `manage.py import_history <center> <file>`, with a `--dry-run`. One row is one past appointment (date, start, end, tutor email, student email, status, modality). People must already be in the center. Rows land on a hidden "Imported history" schedule and term, so they count toward totals and limits but never appear for booking; no email or reminder is sent, and the import is logged. A bad row is listed and skipped, and a second run of the same file adds nothing. Any system's export can be shaped into this layout in a spreadsheet.

**Not done.** It does not read WCONLINE's own Excel files, since none has been seen and guessing at their columns would produce an importer that looks finished and isn't. It makes no session records (the file has no notes), imports no registrations or time-clock entries, and has no web page; a director uses the command line or asks the host to run it.

## Phase 3: the open-content pack (October 2026)

**The mechanism, with no content yet.** `content-pack/` in this repository holds openly licensed text; `manage.py load_content_pack` loads it, `upgrade.sh` runs it with `load_catalog`, and a signed-in person reads an item at `/library/<id>/`. It started as a separate repository in the plan and is in this one on your instruction. What keeps the separation the library document asked for is two folders: `cc-by/` loads everywhere, and `noncommercial/` loads only with `--include-noncommercial` and is in `.dockerignore`, so the image doesn't carry it unless a build copies it in. The code is AGPL and the text keeps its own licenses, which the pack's README says in its first section.

**Each item is a resource too.** Loading makes a `Resource` (catalog id `pack:<id>`, address `/library/<id>/`, link checking off) beside the `ContentItem` that holds the text, so attaching, suggestions by topic, favorites, the record's resource list and the reports all work with no change. `load_catalog` leaves `pack:` resources alone; without that it would have retired them. An item that leaves the pack is marked inactive, never deleted, because records may have it attached.

**Credit is required, and shown first.** Every item names its author, the page it came from, its license and the license's address, and says what changed (or "none"); the loader refuses the whole pack, loading nothing, if any item lacks one, uses a license that doesn't belong in its folder, has an unknown topic, or has no text after cleaning. The page puts the credit above the text. A NoDerivatives item must say `whole: true` and `changes: none`, and the page says it is shown whole and unchanged.

**The text is rebuilt, not trusted.** An item's HTML is rebuilt from paragraphs, headings (a first-level heading becomes second-level, since the page has its own), lists, emphasis, quotations, code, tables and web links, and everything else is dropped: scripts, styles, frames, forms, SVG, images, attributes such as `onclick` and `style`, and any link that isn't http, https or a page anchor. It is cleaned again when shown. This uses Python's standard library; no package was added. Images are left out on purpose, because they often carry a different license from the text.

**What was checked, and what wasn't.** On October 20 the license file at the OpenStax commit a6c9552 was read and is CC BY 4.0 (the repository's README today says CC BY-NC-SA, so only that commit is usable). Writing Spaces essays are CC BY-NC-ND by default under their own Terms of Use, which did not load, and an author may choose another license, so each essay needs its own check; volumes 5 and 6 weren't confirmed. No book called "Technical Writing Spaces" turned up; two technical writing books do exist (LBCC's Maker's Space Edition, CC BY 4.0; the University of Minnesota's, CC BY-NC-SA 4.0). Fetching *About Writing* from the command line returned 403 even with the checker's user agent.

**First items.** On October 20 the OpenStax snapshot (a ZIP from GitHub, 78 MB, outside the repository) was downloaded with your go-ahead and twenty sections were converted into `content-pack/cc-by/openstax-writing-guide/`: thesis and reasoning, paragraphs and transitions, integrating and punctuating quotations, six editing sections (commas, agreement, sentence structure, pronouns, tense, confused words), citation, research and ethics. Each has its own wording unchanged, a summary in our words, and topic tags. Images and embedded exercises are left out.

**Writing Spaces is in the pack.** You said the Writing Spaces licenses are fine to use, so all six volumes (volume 6 is Technical Writing Spaces) were downloaded from their public PDF links on parlormultimedia.com and split by the PDFs' own bookmarks into 107 essays under `content-pack/noncommercial/writing-spaces-vol-N/`. They replace the 38 link-only catalog entries, which were removed so a tutor doesn't see each essay twice. The license on each item is the one printed on that essay's first page: volume 1 and 2 essays are split between CC BY-NC-SA 3.0 and CC BY-NC-ND 3.0, and volumes 3 to 6 are CC BY-NC-ND 4.0. One volume 5 essay prints no notice and was given the volume's 4.0. A NoDerivatives essay is shown whole and with its words unchanged, but its text was extracted from the PDF by machine, so figures and page layout are gone and a heading or table may be flattened; I read that as a format change rather than an adaptation, and you may want to confirm it. The summaries only name the essay and author, because I did not read the essays. Essay PDFs are not committed.

**The 2026 book, in the noncommercial folder.** The PDF you pointed me to (`WritingGuide-WEB.pdf`) is the current OpenStax *Writing Guide with Handbook*, not *About Writing*, and its copyright page says CC BY-NC-SA 4.0. It was split into 33 items (20 chapters and handbook sections 2 to 14) under `content-pack/noncommercial/openstax-writing-guide-2026/`, which loads only with `--include-noncommercial` and stays out of the Docker image. Each item begins with "Access for free at openstax.org," which the license asks every redistributed page to keep. The text was extracted from the PDF by machine, so headings, examples and tables are flattened in places, and each item's change note says so. A few handbook sections start partway down a page, so neighbouring items may share a boundary line.

**The chapter PDFs are committed.** Splitting the book into chapter files gave 226 MB, because the PDF library kept page resources the chapters don't use, and I did not find the cause. You told me to commit them anyway, so they are in `pdf/` beside the items, one per item with the same name; each page keeps its "Access for free at openstax.org" footer. They add that much to every fresh clone of the repository, and nothing in the app serves them yet.

**Not done.** *About Writing* needs a browser-style export or files you supply. The Writing Spaces essays in your Drive folder are CC BY-NC-ND 4.0 (checked on volume 4's Holmes essay), so they can only go in whole and unchanged; the pack's text format would reflow them, and the Drive connector returns text rather than the PDF, so they are not included and the library should link to them instead.

## Phase 3: the de-identified research export (October 2026)

**Only under a protocol, and only while it is current.** A director records the IRB protocol number, the investigator and the dates the approval covers on **De-identified research export** (reports). The export works on days those dates cover and no others, and says why when it can't: no number, no dates, not yet started, ended. Sympraxi can't check any of this with the IRB; it records what a director says, so a download is tied to a protocol number in the audit log, and a lapsed approval stops being usable without anyone remembering to turn it off. Its own permission (`reports.export_research`) goes to directors only, never to site administrators.

**One row per final session record, saying nothing about who.** No names, emails, student, appointment or record IDs, tutors, dates, or anything a person wrote (no summaries, notes, goals, project titles, free-text answers). A session is placed by term and week of the term, its length by a band (1 to 15 minutes, and so on), whether it was in person, online or unbooked, its place among that student's sessions in the file, its concerns, stages and tutor actions by topic key, and the number of resources attached.

**Student codes that can't be joined.** A student is a 12-character code, an HMAC of their ID under a random key made for this one download and never stored. Within a file, one student has one code, so a project can follow someone across sessions. In any other file they have another, so two exports can't be matched, and no one, the center included, can turn a code back into a person. The cost is that a project can't follow students across exports; if it needs to, that is a conversation with the IRB about consent and a different kind of data, not a setting here.

**Small groups are generalized, not dropped.** Dropping rows would bias the data; hiding values keeps every session. Class standing and course appear only if at least five different students share them; otherwise the value is "Other" (the same five the by-course report uses). A course is kept only if it looks like a course code, so a sentence a student typed can never reach the file. A topic used by fewer than five students becomes its parent topic, or disappears. The last table in the file says how many standings, courses and topics were changed.

**What it still can't promise.** Someone who knows the students at a small center may recognize one from the combination of term, week and topics; a project that joins this file with another source can narrow it further. FERPA allows releasing de-identified data once the school has made a reasonable determination that no student could be identified (34 CFR 99.31(b)). This file is built to support that determination, and the page says that the IRB and the registrar make it. Every download, and every change to the protocol, is audited.

**Not done.** No consent flag (a student can't opt out), no suppression of weeks in small terms, and no differential privacy; each is a choice for the IRB, not a default.

## Phase 3: topics by course and class standing (October 2026)

**Which question says "first-year"?** Class standing and course live in answers to questions a center wrote itself, so a director chooses the two questions on **Questions the reports read** (center tools), from the short-answer and choose-one questions on the published registration and intake forms. The choice is stored as the question's permanent key, which every new version of its form keeps. A form doesn't have to be edited, a new version of it doesn't break the report, and answers given to earlier versions still count. A center that hasn't chosen sees "Not given" throughout, and a prompt to choose.

**Where each value comes from.** Standing is the student's latest answer to that question, from registration or any intake form, as it stands when the report is run, not as it was on the day of the session: a student who was first-year in the fall and answered "sophomore" in the spring is a sophomore in both. Course is the answer to the course question on the intake form for the appointment the record is about, and failing that the course of the record's writing project. Text is tidied (spaces collapsed, courses upper-cased) so "eng  101" and "ENG 101" are one course; a choice uses the label of the option chosen.

**What the report answers.** **Topics by course and class standing** (reports, with the same periods, schedule filter and downloads as the statistics) lists sessions and students by standing and by course, the concerns for each standing and course together, and the concerns in each of the center's last eight terms. A **Class standing** filter narrows the whole page, so "what did first-year students come in for this term, by course?" is one choice and one look at the concerns table. Only final session records are counted, as in the statistics.

**Small groups are held back.** A row for fewer than five different students is not shown, and the table says how many rows were left out, the same line the survey results draw. The totals are not changed, so someone with the page can still work out that a group was small; the report is for directors, who can read the records anyway, and the rule makes the page and its downloads safe to pass on. The de-identified research export (the next slice) uses the same rule on purpose.

**Not done.** Standing is not kept as a history, so a report for an old term uses today's answer; a center that cares can ask the question again each term. The report doesn't yet cross concerns with the stage or tutor-action axes.

## Phase 3: writing goals and the timeline across terms (October 2026)

**A goal is a sentence and, if the student wants, a day.** It stays open until someone marks it met or dropped, which keeps who and when; marking it open again clears that, for a mistake. Goals are never deleted, every change is audited, and a student can have 20 open at once, so a list stays a list. A goal can name one of the student's open writing projects. The day, if given, must be from today to two years ahead; one that passes is flagged "past its day", not closed.

**Who writes them.** A student writes their own on **Your writing goals**, reached from My writing. A tutor who works with them (the same test as for their records: an appointment with the student at this center, past or upcoming) or a director writes them with the student, on **Writing goals** from the student's history. One permission, `records.set_goals`, with the usual object rules; front desk staff don't have it. Each goal is part of the education record and is in the student export (now version 8) and the center export (`goals.json`).

**In the brief.** The tutor's pre-session brief now lists the student's open goals above the open writing projects, with a link to add or change them. Met and dropped goals stay out of it.

**One timeline, in terms.** **Across terms** (for staff, from the student's history) and **Your writing across terms** (for the student) merge what the center keeps in separate places into one list, newest first, under the center's terms: sessions, goals when they were set and when they were met or dropped, writing projects when they began, and drafts sent for written feedback and when they came back. Anything outside every term goes last, under its own heading. A session shows its tutor, its project and the first 200 characters of the summary written for the student. Staff notes are never on the timeline. A student sees only their own final records; staff see the records they may open, drafts marked as drafts. Reading a student's timeline is a read of their history, so each one is audited.

**Not done.** A timeline doesn't yet show attendance (no-shows and late cancellations), and goals aren't tied to the topic vocabulary, so the reports can't yet count goals by concern.

## Phase 3: tutor favorites and the resource report (October 2026)

**Favorites are a person's, and show first.** A tutor stars a resource, and it appears under **Your favorites** at the top of the resource panel on the record form, the ones that share a concern with the topics just tagged ahead of the rest, up to eight, never one already attached. A favorite belongs to the person, not the center: a center's own link is offered only in that center, so a favorite of another center's link is simply not shown here, and one the link checker found broken is left out like any other suggestion. Favorites are private. A director sees only a count: how many of the center's tutors favorited each resource.

**Starring works with and without JavaScript.** Beside each resource in the panel is a button that, with htmx, flips the star in place (it is a plain `button` that does nothing without JavaScript, so it can't submit the half-written record). Without JavaScript, **Your favorite resources** (a page of its own, linked from the center's page) lists them with a search to add more, and each add or remove goes through a small page that asks first. The form isn't submitted to star something, which would lose the tutor's unsaved record.

**One report for directors.** **Resources tutors attach** uses the same period and downloads as the statistics (CSV, XLSX, JSON), counts final session records, and names no student. It shows each resource attached in the period with how many records it went on, how many different tutors attached it, how many of the center's tutors favorited it and what the link checker found; the center's own links that nobody attached in the period, with how many records each was ever attached to; and, for each concern tagged, how many records carry it and how many of those got a resource, which is where tutors find something to give and where the catalog falls short.

**Not done.** Favorite counts don't separate tutors who left the center, and the report can't say whether a student opened a resource.

## Phase 3: the link checker (October 2026)

**Off until an installation turns it on.** The checker makes requests from the server to other people's websites, and everything else here either stays inside the stack or goes to something the installation named (the mail relay, the identity provider, the Jitsi server). `SYMPRAXI_LINK_CHECK` is false by default; with it off, the director's page says so and nothing is visited. Nothing new to install: it uses Python's standard library.

**Weekly, in the worker.** The scheduler starts a run when links are due and none ran in the last 20 hours, and hands it to the task worker, which goes through them one at a time. A link is due when it is set to check automatically (a shared entry gets that from `catalog/publishers.yaml`, which keeps Writing Commons and the MLA Style Center manual, as the library document requires) and was last checked a week ago or never. A run checks at most 1,500. A run that has been going for more than six hours is treated as dead, so a worker crash doesn't stop the checks for good.

**Polite.** It reads each site's robots.txt, once per run, and doesn't visit a page the file disallows for it, whether the rule is for everyone or for `SympraxiLinkChecker` by name. It obeys a crawl delay (up to 30 seconds) and waits at least a second between two requests to one site, including the robots.txt request. If a site's robots.txt can't be read (a server error, no answer), the link is left for another day rather than visited without permission. Its user agent begins `Mozilla/5.0 (compatible; ` as Pressbooks needs, then names the checker and the project. It sends HEAD, then GET for servers that refuse HEAD, and reads at most a few bytes.

**It will not be a way into the college's network.** A director can add a link to any address, and the checker runs inside the network, so a link to an internal page could make the server fetch it. Every address a name resolves to has to be public (a name with even one private address is refused, which defeats a name that answers differently each time), and the connection goes to the address that was checked, not to the name a second time. Loopback, private ranges, link-local (including cloud metadata addresses), multicast and reserved addresses are refused, and so is every redirect that leads to one, followed by hand five hops at most. This is tested against a local server and a scripted resolver; it has not been reviewed by anyone else, and a deployment that can reach sensitive internal services should still put the worker where it can't.

**What it concludes.** A page that answers is fine, even after a temporary redirect, or a permanent one that only added a slash, a `www` or `https`. A permanent redirect somewhere else is **moved**, with the new address shown. A 404, a 410, an error or no answer is **didn't answer** the first time, and **broken** once a later check also fails, so one bad night doesn't flag a good link. A 401, 403 or 429, or a robots.txt that asks not to be visited, is **couldn't be checked**, which says nothing about the page. Tutors are not offered broken links in suggestions or search; links that didn't answer yet are still offered.

**Where directors see it.** Under **Links that moved or broke** (center tools, and on the resources page) they see their center's own links that moved or broke, with the new address and a **Check again** button that visits one link now, after an edit, and settles it in one answer. The shared catalog's problems are listed read-only: every center uses those entries, so the project fixes them in `catalog/`, by pull request. Each run, and each manual check, is audited.

**Not done.** No email when a link breaks (the page is the notice), no retry of a robots.txt that failed during a run until the next one, and no checking of links inside a center's uploaded handouts.

## Phase 2: the shared document of a session (October 2026)

**What was added, and approved.** Tiptap 3.32.0 (the editor), Yjs 13.6.33 (the shared document format) and Hocuspocus 4.7.1 (the server and browser provider that carries changes between people), all MIT; and a Node service of its own, `collab/`, which I chose to make as small as possible: one file. You also approved the Node service; esbuild 0.28.2 (MIT) came with it, as a build tool only, because the browser can't load Tiptap's dozens of modules from separate files under a strict policy. It bundles them into one file at `npm run build`, with the packages' license notices next to it. Nothing is loaded from a CDN.

**The service holds nothing.** Sympraxi is where documents are kept. The Hocuspocus service keeps the live copy while people are connected, and loads and saves it through Sympraxi's internal address (`/internal/collab/load/` and `store/`), with a secret that the two share (`SYMPRAXI_COLLAB_SECRET`). Caddy answers 404 to anything under `/internal/` from outside, and the two internal pages are classified in the URL inventory as secret-only endpoints. A save happens two seconds after the last change and at least every ten, so a crash of the service loses a few seconds.

**A token for a person and a document.** The tutor and the students in an appointment open its room page, where Sympraxi signs a token (HS256, the same few lines as for Jitsi) for that person and that document. The service accepts only a token signed with the shared secret, for the document asked for, not expired. A tampered token connects to nothing and saves nothing (tested). The room opens half an hour before the session and takes edits until three hours after it; at other times the page shows what was saved. Directors and front desk staff don't open it: like video, it is for the people in the session.

**Saved as data, shown by us.** The service sends Sympraxi both Yjs's own state (which only it understands) and the same content as a plain ProseMirror document. Sympraxi checks the content's shape and size and stores it. When it shows a document or version it draws it itself from a short list of elements and escapes every word, so nothing a student types can become markup (tested with script tags, a `javascript:` link and an unknown element). Links aren't offered in the editor and are dropped when shown.

**History.** The first change is kept as a version at once. After that, a version is saved when the document changed and the last one is five minutes old, and anyone in the session can save one with a label of their name. Versions are read-only pages. Nothing restores an old version yet.

**Chat is in the same document.** Messages are a Yjs list beside the text, so they are saved and versioned with it, and read-only afterwards. A message's name is whatever the sender's browser says; nothing stops a student's browser from using another name. In a session of two to four people who can see each other, that seemed acceptable, but the stored chat is not proof of who wrote a line. Who opened the room is in the audit log.

**Part of the record.** The document is education-record material like the session record it supports, so both exports include it: the student export (now version 7) holds the text, chat and versions for each appointment the student was booked in, and the center export adds `room_documents.json` and `room_versions.json`. In a group appointment every student in the group wrote in the same document, so each student's export holds it as written.

**Beside the video.** On an online appointment with video on, the room page puts the Jitsi room next to the document in a frame, so a student doesn't leave the page. Only that page allows the video server as a frame source, and only while the room is open, and only the WebSocket address of the editor service is added to what the page may connect to.

**What a strict policy cost.** Tiptap adds a `<style>` element to the page, which the policy blocks, so it is turned off and the few rules it needs are in `sympraxi.css`. Cursors for other people are built with element styles rather than style attributes for the same reason.

**Not done.** Importing a .docx into the document (it would need a converter such as Mammoth, which wasn't on the approved list), restoring a version into the live editor, copying the shared text into the session record's fields, PDF viewing beside the editor, and live captions. The shared document hasn't had a screen-reader test: a live editor is the part of the site most likely to need one.

## Phase 2: comments in the browser (October 2026)

**What was added.** PDF.js 6.4.299 (Apache-2.0, through npm like USWDS and htmx, copied into `static/vendor/pdfjs/` by `npm run build`) and LibreOffice (MPL-2.0), run headless in the task worker to make a PDF from a Word, OpenDocument, rich text or plain text file. Both were approved on October 19. The 3 MB of PDF.js's character maps, fonts and decoders load by name from the same folder; nothing comes from a CDN.

**A viewer on our own canvas.** A tutor opens a student's draft from the submission and reads it in the browser: PDF.js draws each page on a canvas, with its transparent text layer on top so text can be selected, searched and read by a screen reader (the canvases are hidden from assistive technology). The tutor selects text and chooses **Comment on the selected text**, or **Comment on a page** and gives the page number, which is the keyboard route that doesn't depend on selecting. The comment keeps the quoted text and where it was on the page, as fractions of the page's size, so the highlight lands in the same place at any zoom. It works under the existing strict policy: the library, its worker and its fonts are the site's own files, and the new script is a file, not inline.

**A PDF is never opened by the browser.** The page's script fetches the PDF from a URL that sends it as a download no browser runs (`attachment`, `sandbox; default-src 'none'`, no sniffing, no caching), like every file here, and PDF.js draws it. JPEG 2000 images would need WebAssembly, which the policy doesn't allow (`wasm-unsafe-eval` isn't set), so a PDF that uses them shows those images blank; ordinary scans, which are JPEG or CCITT, draw. Reading a file in the viewer is audited, as are adding and removing a comment (ids, not text).

**Who sees what.** The tutor who has the submission comments on the student's drafts, and only while it is theirs. The student sees comments once the feedback is returned, in the same viewer without the tools to comment; directors read them at any time. A tutor can remove their own comment before the return; after that, comments are part of the returned feedback and stay. Both exports include them (the student export holds each draft's comments; the center export adds `comments.json`).

**The conversion is a risk, and it is off by default.** A document is untrusted input to a large program. It runs in a temporary folder under a fixed file name, with its own LibreOffice profile, a stripped environment and a two-minute limit, and the result counts only if it is a PDF no bigger than the upload limit. Macros were already refused at upload and LibreOffice does not run them without a signed macro. But the worker has the same network access as the rest of the stack, so a document that links to an outside address could make LibreOffice fetch it. That is the reason `SYMPRAXI_CONVERT_DOCUMENTS` defaults to off, the worker is a separate image, and this is written here. A later step should run the conversion in a container with no network. The conversion was tested with a stand-in for LibreOffice (its command line, its failures and its timeout) and not with LibreOffice itself, and the Docker stage has not been built; do both before turning it on for a center.

**Not done.** Comments on files attached to appointments (only the queue's drafts have them), replies in a thread, editing a comment, and comments on a Word file's own text are left for later. A converted copy shows the document as LibreOffice lays it out, which can differ from Word.

## Phase 2: Jitsi video rooms (October 2026)

**Optional, and the installation's.** Jitsi isn't added to Compose. An installation points at a Jitsi server it runs (`SYMPRAXI_JITSI_DOMAIN`, `_APP_ID`, `_APP_SECRET` in `deploy/.env`; all three or none), and each center decides whether its online appointments get rooms. The secret stays in `deploy/.env` with the other secrets, and is shared with the Jitsi server (`docs/jitsi.md`). A center without video, or an installation without a server, loses nothing: meeting links work exactly as before.

**A token for a person and a room.** Rooms are named from a keyed hash of the appointment ID (Django's `salted_hmac`), so the name leaks nothing and can't be guessed. Entry needs a signed token, made with the standard library (an HS256 JSON Web Token is a few lines, and not worth a package), holding the room, the person's name and ID, and whether they moderate. It is valid from ten minutes before the start to half an hour after the end, and only the appointment's tutor and its booked students are given one (`online.join`). The tutor moderates and admits students from the lobby, which is a setting on the Jitsi side. No email address goes into the token.

**A redirect, not an embed.** The join page sends the person to their room on the Jitsi domain instead of embedding Jitsi's script, so the site's strict Content-Security-Policy stays as it is and doesn't have to name a second domain. The cost is that a student leaves the Sympraxi window; the room is a full Jitsi page. The redirect response isn't cached and sends no referrer, because the token is in the address. Embedding can come with the live session room (slice 6), where the video sits beside the editor and the policy has to change anyway.

**Links stop being required.** An online tutor assignment normally needs a meeting link. With video on it doesn't, and "Switch a day to online" takes in tutors who have no link. Calendar files for those appointments say to join from the appointment page, since the address isn't one that can be handed out in a file.

**What it doesn't do.** It doesn't record, caption or keep any of the conversation. Who entered which room, when, and whether as moderator is in the audit log.

## Phase 2: the written-feedback queue (October 2026)

**A queue instead of fake time slots.** A student sends a draft with what they want help with and the day they need it by. Nobody books a time. A center turns the queue on under **Written feedback > Settings** (it is off until a director does), and sets the shortest turnaround it will promise (two days to start), how many files a submission can hold (five) and whether to assign automatically.

**Anonymous until claimed.** The queue shows tutors the title, the course, what was asked for and the date, but not the student's name or the draft. The name and the files open once the tutor claims it, the queue assigns it or a director gives it to them. Directors see names throughout, since they can open anything. This is the permission model for it: `queue.submit` (students), `queue.work` (tutors and directors), `queue.view` (the student, the tutor who has it, directors) and `queue.manage` (directors). Front desk staff and site administrators have none of them.

**The feedback is a session record.** Claiming starts a record with no appointment, which is how a meeting that wasn't booked already works, so tutors write on the page they know and everything downstream keeps working: topics, the center's session-report questions, the student's My writing page, amendments after it is final, the FERPA export. Finalizing the record is what returns the submission, through a `record_finalized` signal rather than a second button, so a submission can never read "returned" while its record is still a draft. The student gets the usual "your summary is ready" email. The record starts at 30 minutes and the tutor sets the real figure.

**Commented files stay hidden until the return.** A tutor can send back commented Word or PDF files while the submission is theirs. The student can't open them, or see their names, until the feedback is final. A student can add drafts and remove their own files until then.

**No release.** A claimed submission doesn't go back to the queue. Its record is the tutor's working draft, and a draft that nobody can write would be left behind with the tutor's name on it. A director reassigns it instead, and the draft moves to the new tutor. Students can cancel only while nobody has it; after that, a director cancels.

**Assignment by load, not focus.** The plan said "focus and load." Tutors have no recorded focus yet (the training records in Phase 4 are the natural place), so automatic assignment looks at load alone: each waiting submission, earliest date first, goes to the tutor with the fewest open submissions, until everyone has the center's limit (three to start). A tutor assigned work is emailed that something is theirs, without the student's name or the title.

**Overdue.** The day a student asks for runs to 11:59 p.m. in the center's time zone. The scheduler emails the tutor who has an overdue submission, and each director, once per submission: a count and a link, no names. Marking a submission is done in the same step that picks it, so a second scheduler sends nothing. Returned and canceled work is never overdue.

**Turnaround.** Directors see sent, returned, returned by the day asked for, the typical hours to return (the median) and the overdue count for any dates, with the same figures by tutor. It names tutors, never students, like the other statistics. Both exports list submissions (the student export is version 6; the center export adds `submissions.json` and `submission_files.json`).

**Still to come.** Commenting in the browser, rather than on a downloaded copy, is slice 5.

## Phase 2: files on appointments (October 2026)

**Each file belongs to one student.** Students attach drafts to appointments they're in, tutors to appointments they teach (choosing which student a file is for in a group), and directors to any. A file is opened by the student it belongs to, the appointment's tutor and the center's directors; other students in a group never see it, and front desk staff don't open drafts. Two actions, `files.attach` and `files.view`, with object rules for students and tutors. Files can't be added to a canceled appointment.

**Only writing, checked by content.** PDF, Word (.docx and the older .doc), OpenDocument text, rich text and plain text, up to `SYMPRAXI_UPLOAD_MAX_MB` (25 by default; Caddy's 30 MB request limit has to rise with it). The extension has to match what the content turns out to be, so a program renamed "essay.pdf" is refused. Word and OpenDocument files are opened as the ZIP archives they are: a .docx must hold a document and no macros, an .odt must say it's text and hold no Basic macros, and none may unpack to far more than its size. The older .doc can carry macros and isn't opened, which is one reason to run the scanner. Names are cleaned (no folders, no control characters) and kept only for display; the stored name is random.

**Nothing serves the files.** They live in the `uploads` storage under `media/uploads/`, readable only by the app's user, and come out only through a page that checks who is asking. Every download is forced to save rather than open (`Content-Disposition: attachment`), carries `Content-Security-Policy: sandbox; default-src 'none'` so a browser that opens it anyway runs nothing, and isn't cached. Uploads, downloads and removals are audited. Backups include them, with the rest of `media`.

**ClamAV, if the campus runs it.** With `SYMPRAXI_CLAMAV_ADDRESS` set, every new file waits as "being checked" until the worker has scanned it with clamd, which Sympraxi speaks to directly (the INSTREAM command, a few lines, no package). A clean scan makes it ready. A flagged file's content is deleted at once and the audit log records the signature. If clamd can't be reached the file keeps waiting, and the scheduler asks the worker again after five minutes, up to five tries. Nobody can open a file that hasn't passed. Without the setting, files are ready right away, marked "not scanned". ClamAV is an opt-in Compose service (`--profile clamav`) because its virus database takes about 3 GB of memory.

**Removing keeps the row.** The person who attached a file, or a director, can remove it: its content is deleted, and the appointment still shows that a file with that name was there. Both exports list each file's name, kind, size, SHA-256 and history, never the stored name; the files themselves download from their appointments.

**Still to come.** Signed short-lived links, for opening a file in the browser viewer (slice 5) without a session, and turning documents into PDFs in the worker belong with the viewer.

## Phase 2: moving a day online (October 2026)

**For snow days, one page instead of every appointment.** A director picks a day, on one schedule or all, and every scheduled in-person appointment that starts that day in the center's time zone moves online at the same time. It uses its tutor's meeting link on that schedule, and its room is cleared, so the location becomes the link. A review page lists what moves, and which tutors have no link, before anything changes; a tutor without one stays in person until a director adds a link to their assignment. Everything moves in one transaction. It needs `scheduling.manage_schedules`, which only directors have.

**Everyone affected is told.** Each moved appointment gets a new calendar SEQUENCE and an email to its students and tutor, a new kind (`moved_online`) that says it's now online at the same time, with the link, the director's note if there is one, and an updated calendar file. Placeholders move without emails. Each move is audited as an appointment change, `via` switch_online, with the day.

**Only what's booked.** New bookings for that day can still choose in person. Closing the center for in-person bookings on a day, the other half of a snow day, is left for later; a closure already stops all bookings, if the whole day should go.

## Phase 1: reminders about records not yet written (October 2026)

**One email per tutor, for each session once.** The "Session records to write" page already listed what was missing; now the scheduler also emails the tutor. Each center chooses how long after a session ends (2 hours, 4 hours, a day or two days) or turns reminders off, on **Session record settings**; a new center reminds after a day. A tutor whose sessions fall due in the same sweep gets one email listing them, with how many records each still needs and a link to the appointment and to the page of everything left to write. Each appointment gets one reminder, ever: `RecordReminder` is written in the same transaction as the email is queued, with a unique constraint on the appointment and tutor, so two schedulers or a repeated sweep send nothing more. Sending a second, later reminder would be easy to add, but one email with a page that stays current seemed enough to start.

**Who needs a record.** A student who came or wasn't marked, and hasn't left the group, needs a final record; a draft doesn't count as written. No-shows don't need one, and the email says to mark a student as a no-show instead of writing a record for someone who didn't come. Canceled appointments and placeholders get no reminders. A sweep looks back only two days past the due time, so turning reminders on, or a scheduler that was down, doesn't email about months-old sessions. A tutor whose tutor role is turned off gets none. Like the booking emails to tutors ("Sign in to see who it is"), the email names no students: the links need a sign-in.

## Phase 1: the record of disclosures (October 2026)

**What FERPA asks, and nothing more.** 34 CFR 99.32 asks a school to record each request for, and each disclosure of, a student's education records to anyone outside its own officials: who asked or received them and their legitimate interest, kept as long as the records are, and open to the student. Each entry here says whether records were disclosed (a refused or open request is recorded too), the day it was asked for and the day it was disclosed, who, their legitimate interest (for a health or safety emergency, the threat), the 99.31 provision or written consent it relied on, which records, and a note. Disclosures to the student, to the center's own staff, and of directory information don't need one (99.32(d)); nothing stops a director recording one anyway. Sympraxi doesn't send records anywhere itself, so the entries are made by hand when a director sends something outside the center. A full-center export, which goes to the center's own directors, still isn't one ("Phase 1: statistics, master lists and exports").

**Entries can't be changed.** A database trigger (privacy migration 0004) refuses UPDATE always and DELETE unless the transaction sets `sympraxi.records_purge`, which only the future retention purge of the student's records will do; the record of disclosures has to last as long as they do. A mistake is fixed by a new entry that names the one it corrects, so the student's record shows both. Only an entry about the same student in the same center can be corrected.

**Directors keep it; the student reads it.** One new action, `privacy.record_disclosures`, for directors only; site administrators get nothing, as with every other part of a student's record. Directors reach a student's record of disclosures from their session history, and reading it is audited (`privacy.disclosures_viewed`), like the history. Recording an entry is audited too, with the provision relied on, never the words. The student sees theirs from My writing, under "Who outside the center has seen your records". The student record export (format version 4) and the full-center export include every entry.

## Phase 1: announcements and mass email (October 2026)

**Announcements are plain text for a span of days.** A director posts one for everyone in the center, for students, or for staff, with a first and a last day (at most a year apart). It shows at the top of the center page, and students also see theirs on the schedules page, where they book. The text is escaped like everything else; line breaks become paragraphs and web addresses become links (Django's `linebreaks` and `urlize`), and nothing else is interpreted, so an announcement can't carry markup or scripts. Announcements aren't records, so changing or deleting one isn't audited. Two new actions, both for directors only: `notify.manage_announcements` and `notify.send_mass_email`.

**Mass email reaches one group, and the director sees how many first.** The groups are students, tutors, front desk staff, directors, all staff, or everyone, and students can be narrowed to those with an appointment (not canceled, and not one they left) in a span of days, on one schedule or all. Writing goes to a review page that says how many people it reaches and how many students it leaves out, offers a test copy to the director alone, and only then sends. Each person gets their own copy, so nobody sees another address, and replies go to the center's contact address, or to the director if the center has none.

**Students can turn off center news; staff can't.** A new setting on the email settings page, on by default, lets a student stop mass email from centers where they're a student. Emails about their own appointments still come. Staff get mass email whatever they chose, because it's about their work, and someone who is both a student and staff in the center counts as staff. A student's copy says how to turn center news off; a staff member's doesn't.

**Every send is logged with who it went to.** The log keeps the subject, the message, the group in words, who sent it and when, how many students were left out, and each recipient. Directors see it under **Emails sent**, so "did they get it?" has an answer months later. Sending is audited (`notify.mass_email_sent`) with the group and the counts, never the message. The request only writes the log; the task worker then queues each person's copy through the same queue as every other email, a few hundred at a time, marking each recipient as it goes, so a worker that stops partway picks up where it left off and nobody gets two copies.

## Phase 1: private calendar feeds (October 2026)

**One feed per person, across centers.** Anyone signed in can turn on a calendar feed under **Account** → **Calendar feed** and subscribe to it in Google Calendar, Outlook or Apple Calendar. It lists the appointments they booked as a student and the ones they teach as a tutor, in every center where that role is on, from a month ago to six months ahead. Canceled appointments drop out, and calendar apps remove them at their next fetch. The `.ics` file attached to booking emails still works as before; a feed is for people who want every appointment without adding each one.

**The address is the only key, so it's treated like a survey link.** Only a SHA-256 hash of the token is stored, with a prefix of its own so it can never match a survey link's hash. The address is shown once, on the page right after it's made, and then only its hash exists. People can replace it (the old address stops working) or turn the feed off. Unknown, replaced and turned-off addresses, and addresses of accounts that were turned off, all get the same 404, and the URL inventory test checks that. The access log and Django's log write `/calendar/[link].ics` in place of the token (`sympraxi/core/logs.py`). Calendar apps fetch the address without signing in, so the staff two-factor gate leaves `/calendar/` alone, as it does `/survey/`. A feed records when it was last fetched, at most once an hour, so the page can say whether a subscription is still in use; the fetches themselves aren't audited. Turning a feed on, replacing it and turning it off are.

**Events never name students.** A calendar app keeps its copy on its company's servers, so a tutor's feed would otherwise send student names to Google or Microsoft. Each event says when, where (the room or the meeting link) and the center, calls a tutor's appointments "tutoring appointment", and links to the appointment in Sympraxi, which needs a sign-in. A student's own events name their tutor, as the booking email already does.

## Phase 1: the time clock (October 2026)

**A basic time clock, as Phase 1 plans.** Tutors, front desk staff and directors clock themselves in and out on the center's **Time clock** page, choosing what they're working on: tutoring, training, a staff meeting, front desk or office work, or other. They see their own hours for this week and last. Directors see **Timesheets** for any dates up to a year, with hours by person and category and every entry, and download them as CSV, XLSX or JSON like the reports. The categories are fixed for now; a center choosing its own, network limits on where people clock in, and approvals are Phase 4's full time clock. Two new actions: `staff.clock_own` (tutors, front desk, directors) and `staff.manage_time` (directors). Site administrators get neither: the hours are the center's employment records.

**Nobody changes their own hours after the fact.** A director adds an entry someone forgot, changes one, or removes one, and has to say why each time. The audit log keeps the reason with the entry's times and category before and after; the note's words stay out of it, as with every audit event. A removed entry is kept and marked removed, so it stops counting without disappearing, and the full-center export lists removed entries too. An entry may be at most 16 hours long and can't be entered before the time was worked.

**The database keeps the rules.** An entry ends after it starts; a person has at most one open entry in a center; and a person's entries in a center never overlap, through an exclusion constraint on the time range (an open entry's range has no end, so nothing can be added after it until it closes). Removed entries are left out of both. Clocking in twice, or clocking in over time a director already entered, gets a plain message instead of an error.

**Midnight clocks people out.** Anyone still clocked in at midnight in the center's time zone is clocked out at midnight by the scheduler, and the entry is marked. The person sees the mark on their page, and directors see a count to check on the timesheet; changing the entry clears the mark. WCONLINE does the same. The alternative, leaving entries open until someone notices, puts days of hours on a timesheet by accident.

**Hours count on the day an entry starts.** A shift from 10 p.m. to 1 a.m. counts on the first day. Hours are rounded to the hundredth for each category, and the totals add those. An open entry counts as an entry with no hours until it closes.

## Phase 1: adding people and CSV import (October 2026)

**Directors add people in Sympraxi.** Until now only a site administrator could give someone a role, in the Django admin. The People page now lets anyone with `center.manage_members` (directors, and site administrators) add one person, add many from a CSV file, turn a role on or off, add a role to someone, and turn one role off for everyone at once, as at the end of a term. No new action was needed. The rules are in `sympraxi/centers/people.py`.

**Someone new gets an account with no password.** Their address is stored unverified. They claim the account with single sign-on, which matches it by the address the provider vouches for, or with "Forgot your password?". A local sign-in then still asks them to confirm the address by email, because a password reset doesn't mark it verified in allauth; two emails, but nothing new to build. A welcome email is optional. It says how to sign in and holds no link that signs anyone in.

**Single sign-on verifies the address it links, after allauth's password wipe.** allauth takes the password off an account matched by an unverified address, in case someone else registered it first. Sympraxi now also marks the address verified when the link is saved, so an imported person isn't asked to confirm it by email after signing in with SSO. This has to happen after the wipe: marking it in `pre_social_login()`, which runs before, would let a squatter keep their password. `test_a_signed_up_squatter_loses_the_password_before_the_address_is_verified` fails if it moves there.

**An import never changes an existing account, and never says whether there was one.** Name, pronouns and student ID belong to the person; another center can't rename them, so a matching account just gets the role. The preview says, for each line, only whether the role will be added, turned back on, or is already here. Saying "new account" or "existing account" would let a director look up whether anyone has an account, and with what name. Account creation is audited as a site-level event (`access.account_created`), outside any center's log.

**A file is checked, previewed, then applied all at once.** Columns are found by their headings, without regard to case, spaces or punctuation, in any order: Email, and Full name or First name and Last name, then optional Preferred name, Pronouns, Student ID and Role. A role cell may be blank, and the form then supplies one. Files are read as UTF-8, with or without Excel's byte order mark, or else as Windows-1252, which Excel's plain "CSV (Comma delimited)" writes; commas, semicolons and tabs all work. Each line is checked: a real address, at a college domain when `SYMPRAXI_SIGNUP_EMAIL_DOMAINS` is set; a name; a known role; field lengths; no person in the same role twice; no student ID that another line or another account has. Lines with problems are listed and skipped; the rest wait in the director's session until they confirm. Confirming adds everything in one transaction, and if an account changed in the meantime (someone took a student ID), nothing is added and the director chooses the file again. A file is limited to 5,000 people and 2 MB.

**Turning a role off keeps it.** A membership is turned off, never deleted, so its history stays and it can be turned back on; an import turns it back on too. The person's appointments and records stay. Turning a role off for everyone first shows how many people it changes and how many have appointments still to come, which stay on the schedule. Directors can't turn off their own director role, alone or in bulk, so a center can't be left without one by accident. Every membership added, turned on or turned off is audited with how (`via`), and an import and a bulk turn-off each add one summary event.

## Phase 1: statistics, master lists and exports (October 2026)

**Reports are counted in PostgreSQL.** A term's statistics at a busy center cover thousands of appointments. Each table on the statistics page is one grouped query, and no appointment, visit or session record is loaded into Python to build it; a test fails if one is, and another checks that adding appointments adds no queries. The hours report adds up tutors' weekly hours in Python, day by day, so its cost grows with the number of tutors and days and never with the number of appointments. A report covers a term or up to a year of dates, on one schedule or on all of them, in the center's time zone.

**A visit is one student in one appointment.** Attendance belongs to each student ("Attendance belongs to each student, not to the appointment", below), so statistics count visits, and a group of four is four visits. Each visit has one outcome: came, no-show, late cancellation, canceled, or not marked. Waived no-shows and late cancellations still count as what they were, because a waiver only takes them out of the count toward a block. Placeholders hold time without a student, so they have no visits, and the summary counts them on their own line. Each appointment has one kind, checked in this order: walk-in, group (room for more than one student), part of a weekly series, single booking. Tentative isn't one of them, because a tentative appointment stops being tentative when staff confirm it.

**A first visit is the first time a student came to the center.** That means the first visit marked "came" on any schedule, at any time. A student who first came last term, or first came on another schedule, is on a return visit. Counting first visits within each period would have made every returning student new again each term.

**Topics come from final records only.** A draft can still change. A record for a meeting that wasn't booked has no schedule, so it counts only when the report covers every schedule.

**No survey data in the reports.** Survey results stay where the surveys slice put them: by term, from five responses, for directors ("Results by term, from five responses", below). Splitting them by tutor, week or schedule would make groups small enough to pick out a student. The full export holds them only as the results page shows them.

**Hours offered come from the weekly hours as they are now.** Weekly hours and changes to them aren't kept as a history, so the hours offered in a past term are worked out from each tutor's current hours across the whole period, and a tutor marked as not taking appointments offers none. A tutor who left mid-term and was turned off shows booked hours and no hours offered; a tutor hired mid-term shows hours offered for the whole term. A history of weekly hours would fix both. Booked hours are the length of each appointment that wasn't canceled and isn't a placeholder, counted once however many students joined. Attended hours are the booked hours of appointments at least one student came to. Every week in the period gets a row, so a week the center was closed shows zeros.

**Three new actions.** `reports.view_statistics` (directors) covers statistics and hours. They name tutors, not students, and like survey results they aren't audited. `reports.view_master_lists` (front desk and directors) covers the appointment list and the student list, which name students. `reports.export_center` (directors) covers the full export, and any director of the center may download an export another director asked for. Site administrators get none of the three. Tutors don't get the lists either; they see their own appointments on their tutoring schedule.

**The lists are audited with the students they name.** Each view or download of the appointment list or the student list writes `reports.list_viewed` or `reports.list_exported` with the filters and the IDs of the students it showed, the way `records.history_viewed` lists the records shown. The student list shows 250 students a page, so one page view names at most 250; a download names every student in it. The appointment list stops at 3,000 appointments and says so.

**Lists that print.** Both lists are tables with column and row headers. The print stylesheet drops the site's menus, the filters and the download links, repeats the column headers on each page, keeps each row on one page, and starts each day of a week on a new page. There are no inline styles or scripts, which the Content Security Policy would block.

**A download holds what the page shows.** Each report downloads as CSV, XLSX or JSON from its own address with `?format=`, built from the same tables as the page. A CSV of a report with several tables stacks them, each under its title. An XLSX file has a sheet for each table and a first sheet with the filters. JSON keeps every value as it is. Downloads and the list pages are sent with `Cache-Control: no-store`.

**Text that a spreadsheet would run gets an apostrophe.** Anyone can make a name or an answer start with `=HYPERLINK(...)`, and a spreadsheet opening the CSV would run it. In CSV and XLSX files, a text cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading `'`, as OWASP recommends, so the spreadsheet shows the text. Numbers stay numbers, negative ones too. The XLSX writer is also set never to turn text into a formula, a link or a number. JSON is left alone: programs read it and need the exact text.

**XlsxWriter writes the XLSX files.** It is the one new dependency (BSD-2-Clause, version 3.2.9, nothing else pulled in). It only writes, which is all reports need, and it can be set never to read text as a formula. The alternative, openpyxl, stores any text that starts with `=` as a formula unless each cell is forced to text.

**The full export is one ZIP, built by the worker.** A director asks for it on the export page and the `worker` builds it. Everything is read in one read-only REPEATABLE READ transaction, so the file shows the center at a single moment. Each table is read in chunks, and the ZIP goes to a temporary file as it's written. The file is then saved in the `exports` storage (`media/center-exports/`, readable only by the app's user), and the director who asked gets an email that links to the export page, not to the file. Everything is JSON, with CSV copies of the appointments and the audit log and a manifest that says what each file holds. A center has one export on the way at a time (a partial unique index). One still queued or building after six hours is marked failed, so a worker that stopped doesn't block the next.

**What the export holds.** People and roles, terms, closures, rooms, schedules with each tutor's assignment, weekly hours and changes, every appointment with each student in it and their attendance, exemptions with their notes, booking blocks, writing projects, every session record (drafts too) with staff notes, topics, resources, report answers and amendments, the forms with every version's questions and option keys, every registration and intake response, survey results as the results page shows them, the center's own resources, staff time clock entries (removed ones marked), and the center's audit log. Unlike the student export, it doesn't hide other students, because it's the center's own copy of its records. Nothing about other centers is in it. No survey response is ever listed, with or without its ID or date. The audit log's text goes through the same scrubber as the server logs, though no audit event holds a survey link today.

**The download link works for 24 hours.** Asking for an export writes `reports.center_export_requested`, and each download writes `reports.center_export_downloaded`. When the link expires the scheduler deletes the file and keeps the row, so the page still shows who exported the center and when. An expired link, or a file that's missing (after a restore, say), gets a page that says so, with status 410. Neither Caddy nor Django serves the folder, and `backup.sh` leaves it out, so an export doesn't outlive its link inside a backup kept for a year. Everything in it is in the database dump anyway.

**An export isn't recorded as a disclosure.** It goes to the center's own directors, who are school officials with a legitimate educational interest, and 34 CFR 99.32(d) doesn't require recording disclosures to them. When the disclosure log comes, a director who sends the file outside the center will have to record that there; Sympraxi can't tell when it happens.

## Phase 1: sign-in limits and web workers (October 2026)

Two fixes from the first-Monday load test, which found the weak points of a rush in password sign-ins and server capacity.

**Rate limits count each visitor's own address.** allauth counts its limits per client address, and it reads `X-Forwarded-For` only when `ALLAUTH_TRUSTED_PROXY_COUNT` says how many proxies to trust. That wasn't set, so behind Caddy every request counted as Caddy's, and all of a site's password sign-ins shared one limit of 30 a minute. In the load test, 150 sign-ins in one minute let 30 people in and gave the other 120 allauth's bare "Too Many Requests" page. settings.py now sets the count to 1 whenever `SYMPRAXI_TRUST_X_FORWARDED_FOR` is on, as `deploy/compose.yaml` has it. allauth then takes the last `X-Forwarded-For` entry, the one Caddy writes, which is also the address the audit log records; a test checks that the two agree. Any earlier entry would have come from the client, so allauth ignores it. This assumes Caddy is the only proxy. With a load balancer in front of Caddy, the address Caddy passes on is the load balancer's, and everyone shares the limits again.

**Per-address limits allow for a campus network.** With a count for each address, students who share one public address on campus Wi-Fi still share a count. allauth's defaults are 30 sign-ins, 10 failed sign-ins and 20 sign-ups a minute from one address. After 10 failed sign-ins in a minute, allauth refuses every sign-in from that address, correct passwords included, so ordinary typos during a rush could lock out a whole campus. The limits are now 300 sign-ins a minute (twice the busiest minute in the load test), 60 failed sign-ins (one in five) and 60 sign-ups. Each account keeps allauth's limit of 5 failed sign-ins in 5 minutes, and password resets keep allauth's 20 a minute per address. The cost is that an attacker at one address can try 60 passwords a minute across different accounts instead of 10. The limits are fixed in settings.py, not read from `deploy/.env`. A center that outgrows them can turn on single sign-on, which doesn't count toward them.

**A page for the limit.** allauth shows a `429.html` template when a limit is reached, and there wasn't one. `handler429` in `sympraxi/urls.py`, where allauth looks first, now renders `sympraxi/templates/429.html` with a `Retry-After` header of 60 seconds. Every allauth limit that answers with this page counts over one minute (signing in, signing up, resetting or changing a password, changing an email address, confirming a password), so a minute is always long enough to wait. A test fails if any of them gets a longer window. Someone signed in is told about their account's limit, and anyone else about their address's. The page passes axe and keeps to the Content Security Policy (`tests/e2e/test_rate_limit_page.py`).

**The number of web workers is a setting.** The Dockerfile fixed Gunicorn at 3 workers. It now sets `WEB_CONCURRENCY=3`, which Gunicorn reads as its worker count, and no longer passes `--workers`, so `WEB_CONCURRENCY` in `deploy/.env` sizes an installation. The default stays at 3. `docs/install.md` suggests twice the vCPUs plus one and about 150 MB of memory per worker; a Django process measured on Windows after serving a few pages used about 110 MB. The count isn't worked out from the number of processors, because inside a container that is the host's number, and on a large shared host it could open more database connections than PostgreSQL allows (100 by default). The CI smoke test starts the stack with `WEB_CONCURRENCY=2` and counts the Gunicorn processes.

**Static files stay with WhiteNoise.** Static files were 42 percent of the load test's requests but took about 3 to 4 percent of the workers' time, estimated from each kind of request's count and its median time after the first two minutes. That median was under 3 ms for static files and about 20 to 140 ms for pages. WhiteNoise serves the compressed copies made when the image is built and tells browsers to keep the hashed files for ten years, so a student loads them once until an upgrade changes them. For Caddy to serve `/static/`, the files would have to reach it through a volume the web container fills at startup or through a Caddy image built with them. Either way, during an upgrade a page could name new files before Caddy has them. Moving static files would free 3 to 4 percent of the workers' time, and a fourth worker adds a third more.

## Phase 1: booking page fixes after the load test (October 2026)

These fix three of the findings from the first-Monday load test (below). The booking rules in `services.py` didn't change. Three choices here change what people see and were made as defaults; the paragraphs on them name the alternatives.

**Students don't see times with a tutor who is full.** Once a tutor has reached their daily or weekly cap on a schedule (`max_per_day`, `max_per_week`), open times leave out that tutor's new times for the day, and a link to one of them gets "That time isn't open anymore." Seats in the tutor's group appointments stay listed, because joining a group doesn't count toward a cap. `availability.at_cap()` counts what `services._check_tutor_caps()` counts: the assignment's active appointments that start that local day or week, without placeholders. The appointment being moved isn't counted on the change page, as in `services.reschedule()`, so a student whose tutor is full that day can still move to another time with them that day. A new property-test rule books only times taken from the student's own list and fails if one is refused for anything but the student's own limits or calendar.

**Staff still see those times, marked.** Front desk staff and directors can book past a cap with "Book even if it goes over the student's or tutor's limits", so their list keeps those times, tagged "Tutor's daily limit reached" or "Tutor's weekly limit reached", and the staff booking page says the box is needed. The alternatives were hiding them from staff too, which would leave the box useful only for student limits, or showing them untagged as before, so the front desk found out only when the booking was refused. To change it, pass `caps="hide"` (or `"ignore"`) where `open_times_page` and `staff_book` pass `"mark"`. Moving an appointment has no override, so the change page hides those times from staff as well, except when the appointment is a placeholder, which no cap applies to.

**A second post of the booking form shows the booking.** When a student posts the booking form for a tutor and time they already hold (same assignment, start and end, in an active appointment), the page takes them to that appointment with the message a single click gets ("You're booked. A confirmation email is on its way." or the tentative one). The view checks before booking and again after a refusal, since the other click can commit while this one waits on the student's lock; a test sends two posts through the view at once. Opening the booking page later for a time they hold (Back, a reload, an old tab) goes to the appointment with "You already have this appointment." The alternatives there were the usual success message, which would describe a booking made earlier as new, or no change, which tells the student the time is gone. The staff booking page doesn't do this: posting one student and time twice still gets "already has an appointment then", since another staff member may have made that booking.

**The booking forms ignore a second click.** `sympraxi/static/sympraxi/sympraxi.js` is Sympraxi's first script of its own. It loads from a file on every page, so the CSP doesn't change. A form marked `data-submit-once` ignores a second submit until the page changes, and its buttons get `aria-disabled`, which USWDS draws as unavailable. They aren't made `disabled`, because a disabled button is left out of the submission, and the form builder's Continue button needs its name to arrive. A page brought back by the Back button can be sent again. Only the student and staff booking forms have the attribute; the alternative was every form that changes something (cancel, move, confirm, attendance), which is a matter of adding it to those forms. Without JavaScript, the server check above still covers the student's form. The browser test clicks twice 150 ms apart while the booking is slowed; without the attribute Chromium sends both.

**Messages use plural forms.** A limit message now reads "That would go over the limit of 1 appointment a day" (likewise for weeks, terms and minutes), and the horizon message reads "You can book up to 1 day ahead." Both go through `ngettext`. A front desk refusal for a single booking no longer starts with the date; a weekly series still names the week that was refused.

**The load test again, on October 16, 2026.** Same standard run and machine, at phase-0-foundation's a502cee plus these changes. It passed every check, with no server errors or deadlocks and every page's p95 under 215 ms. Students got no "This tutor is fully booked that day." refusals; the two earlier runs had 182 and 207. The front desk still got 72 (53 and 76 before), since the simulated workers pick tagged times and never check the override box. With fewer wasted tries there were 1,018 attempts (683 booked, 335 refused), and 499 of 500 students got at least one appointment, against 487 and 481. "That time isn't open anymore." came up 185 times, about as often as before (171 and 207). Of the 36 double-clicks, 30 booked, and in all 30 both requests ended on the appointment with the booking message. The load client sends raw HTTP, so this measures the server check alone.

## Reflow, staff pages on phones and focus rings (October 2026)

The accessibility notes listed three more checks to add: pages at 320 CSS pixels wide, the tutor's and front desk's pages on a phone, and a focus ring on every control. `tests/e2e/test_accessibility.py` now runs all three. The student pages fit at 320 pixels and the staff pages passed axe on a phone. The checks found five tables too wide for 320 pixels and two kinds of disclosure that showed only the browser's own focus ring.

**Reflow is checked at 320 by 256, in a desktop browser.** WCAG's reflow criterion (1.4.10) imagines a 1280 by 1024 window zoomed to 400%, which leaves 320 by 256 CSS pixels, and the test uses that size. It covers the phone pages and the pages with the widest tables, and fails if `document.documentElement.scrollWidth` is over 320, naming the elements that stick out. USWDS sets `overflow-x: hidden` on the body, so a page too wide for the window doesn't scroll sideways; what doesn't fit is cut off, with no scroll bar to reach it. `scrollWidth` still counts what was cut.

**Wide tables stack instead of scrolling.** The criterion lets a data table scroll sideways inside the page. Most of Sympraxi's tables already use USWDS's stacked table, which below 480 pixels shows each row as a block with each cell under its column's name. Five didn't: the members list, the list of forms, a form's published versions, the survey results and the passkey list. All five stack now. A scrolling wrapper would keep each row on one line, but it hides columns past the edge with nothing to say they're there, and a keyboard user can scroll it only if the wrapper takes focus itself, which needs a tabindex, a role and a name on each one (axe's `scrollable-region-focusable` rule). Stacking needs none of that and matches the rest of the site. allauth's generic table element keeps its plain table, since its cells have no column names to show and Sympraxi's own copy of the passkey list replaced its only use.

**Staff pages on a phone join the phone list.** The record form (started and as a draft) and the front desk's open times, booking for a student, day sheet and possible no-shows are checked at 375 by 812 like the student pages: axe as each loads and with the menu open, and no sideways scrolling. They passed as they were.

**Focus rings are checked by tabbing.** axe has no rule for visible focus (2.4.7). `test_each_control_shows_a_focus_ring` presses Tab through eight pages, from the skip link until focus comes back around, and compares each control's computed outline and box shadow with what they were before anything had focus. A control fails if neither changes, if its ring is outside the window, or if its only ring is the browser's own (`outline-style: auto`). That last rule goes further than the criterion, which any visible ring meets. The browser's own ring differs from one browser to the next, so a reviewer would have to check it in each, while USWDS's is the same everywhere. USWDS keeps the real checkbox and radio button off-screen and rings the box it draws on the label, so for those the test reads the label's `::before`. A second test does the same on a phone-sized screen, on the page and then inside the open menu. Neither judges the ring's contrast with what is around it, which stays a manual check.

**Disclosure summaries get USWDS's ring.** USWDS gives its 4-pixel ring to links, buttons, fields and anything with a tabindex, but not to `<summary>`. The record form's topic groups and the form builder's "Throw away the draft" are summaries, so they had only the browser's own ring: a thin dark line in Chromium, and something else in each other browser. Sympraxi's stylesheet now gives `summary:focus` the same ring as everything else.

**Sign out looks like the menu's links.** In the phone menu, Sign out, a form button made to look like a link, was darker (#1b1b1b) and taller (1rem of padding on every side) than the USWDS links above it (#565c65, 0.5rem by 1rem). It now takes their color and padding, and keeps the bold text and 1rem padding of the desktop header.

## Accessibility checks on phones, after htmx updates and with emulated settings (October 2026)

The accessibility notes listed three states axe never saw: a phone-sized screen with the menu open, content htmx swaps in, and forced colors or reduced motion. `tests/e2e/test_accessibility.py` now checks each. axe found one problem, in the menu's close button.

**Phone size is 375 by 812, with touch.** That is a common phone's viewport in CSS pixels. The browser context also says it is a mobile device with a touch screen, so the page lays out as on a phone and the menu opens with a tap. Eight student pages are checked: signing in, My centers, the center page, a day's open times, booking, my appointments, one appointment and a session on My writing. axe runs on each twice, as the page loads and with the menu open, because the open menu's overlay covers the page and axe can't check the contrast of anything under it. Before the second run the test waits for the menu to finish sliding in.

**A script checks the menu's focus trap, because axe can't.** While the menu is open, USWDS puts `aria-hidden` on everything outside it, so screen readers skip the page behind it. The links back there can still take focus, and axe can't tell whether Tab reaches them, so it marks its `aria-hidden-focus` rule as needing review instead of passing or failing it. USWDS's focus trap is what keeps them out of reach. `test_the_phone_menu_keeps_focus_inside_until_closed` opens the menu by keyboard, presses Tab and Shift+Tab, and fails if focus leaves the menu. It also checks that Escape closes the menu, puts focus back on the Menu button and takes `aria-hidden` off the page. Using the `inert` attribute instead would mean JavaScript of Sympraxi's own, which it doesn't ship.

**The htmx checks reuse the keyboard tests' steps.** The steps that make htmx swap content in are functions shared by the keyboard tests and `test_swapped_in_content_passes_axe`: changing the date on open times and on the page for moving an appointment, choosing an answer that has a follow-up question, tagging a topic and attaching the suggested resource, searching the resources and the members, and moving a question. Sharing them keeps the two sets of tests from drifting apart. axe runs after each step, once htmx has no request out and has finished settling, since some changes (hiding "Nothing attached yet," for one) happen only after its settle delay. The test also fails if the page reloaded, so a broken htmx attribute can't pass by falling back to a full page that was already tested.

**Forced colors and reduced motion run separately.** Playwright's `forced_colors="active"` and `reduced_motion="reduce"` change which media queries Chromium matches. Eight pages that between them use most of the USWDS components Sympraxi does are checked under each, one setting at a time so a failure names it, and each test first checks that the media query matches, so it can't pass after the emulation stops working. The open phone menu is checked under each too, since USWDS's styles for both settings change it: under forced colors the close button's image is swapped for a drawn X, and under reduced motion the menu no longer slides in. That test fails if anything is animating right after the menu opens.

**axe's color rules are off under forced colors.** With forced colors, axe compares the page's own text colors with the forced background rather than the colors the browser draws. Under a dark theme it reported near-black text on black on every page, though the screenshots showed white and yellow on black; under a light theme the same mistake passes by luck. So `color-contrast` and `link-in-text-block` are turned off in those runs, and contrast in a real Windows contrast theme stays a manual check. The other rules still run, and one of them caught the close button below, because USWDS's forced-colors styles hide some elements and draw others.

**The menu's close button is named by hidden text.** Its name came from the alt text of its X image. Under forced colors USWDS hides that image and draws the X with CSS instead, so in a contrast theme the button had no accessible name. The image now has empty alt text, and the button holds "Close menu" in a `usa-sr-only` span, which forced colors leave alone.

## Fixes from the security and accessibility drafts (October 2026)

Drafting the HECVAT answers (`docs/security-questionnaire.md`) and the accessibility notes (`docs/accessibility.md`) turned up gaps that could be closed in code. These are the choices made in closing them.

**Two-factor secrets are encrypted in the database.** allauth stores each authenticator app's TOTP secret, and the seed the recovery codes are made from, in `mfa_authenticator.data`, and its default MFA adapter stores them as they are. Anyone with a database dump or a backup could then make any person's codes, and a site administrator could read them in the Django admin. `MFAAdapter` now encrypts them with Fernet (AES-128 in CBC mode with an HMAC-SHA256 tag, from the `cryptography` package) before allauth saves them (`sympraxi/accounts/encryption.py`). Accounts migration 0004 encrypts the ones stored before it and skips any that are already encrypted. Passkeys hold only a public key and aren't changed. The secret allauth keeps in the session while someone is setting up an app isn't covered: it can't sign anyone in until they confirm a code, and allauth drops it then.

**The key comes from SECRET_KEY.** A separate key would sit next to SECRET_KEY in `deploy/.env`, with the same readers, so it would protect nothing more and be one more thing to lose. The Fernet key is derived from SECRET_KEY with HKDF and a label used for nothing else, so it never equals the key Django signs with. A backup restored without the SECRET_KEY it was made under therefore leaves every authenticator app and recovery code unreadable, for the campus as for a thief, so install.md says to keep a copy of the key.

**Changing the key uses Django's fallbacks.** `SYMPRAXI_SECRET_KEY_FALLBACKS` sets `SECRET_KEY_FALLBACKS`. Secrets written under a fallback still decrypt, and `manage.py reencrypt_mfa_secrets` rewrites them under the current key, after which the fallback can go. Django uses the same setting to keep sessions and reset links working during the change. A secret no key can read makes the code check fail with a server error whose log message names the setting, instead of quietly calling every code wrong. If the old key is lost, `--remove-unreadable` deletes those authenticators and records each removal in the audit log, and their owners set up two-factor login again.

**Checkboxes show their hint and their error.** `includes/field.html` drew a checkbox with only its label. Its help text and its error never appeared, though the box's `aria-describedby` already pointed at a hint that wasn't there. The form builder's error for a required demographic question was one nobody saw: the page came back with no message. The hint now sits under the label, lined up with the label's text, and an error puts the box in a USWDS error group with the message above it. Both are tied to the box as other fields' are, and a test checks that `aria-describedby` never names an element missing from the page. The question form's checkbox hints, which were loose paragraphs, now come from the field. allauth's own field element ties its errors to the input the same way.

**Error pages use the site's layout and show nothing from the request.** Django's plain 403, 404, 500 and CSRF pages had no header, navigation or way back. `403.html`, `404.html`, `500.html` and `403_csrf.html` now extend `base.html`. The 404 page doesn't show the path or the exception, so a student who opens another student's appointment gets the same page, byte for byte apart from the CSRF token and the CSP nonce, as for an appointment that doesn't exist; a test compares the two, and a third from another center. The 500 page is rendered without the request's context (`core.views.server_error`), as Django's own handler does, because the user, session and message context processors read the database, which may be what failed. It gets only the site name, so its navigation offers just the home page. A failed CSRF check has its own view (`CSRF_FAILURE_VIEW`), because Django's default renders the template without the request's context. Its page says nothing was saved and what usually causes it; the reason goes only to Django's log.

**The rest of allauth's pages are axe-tested.** The browser tests covered allauth's sign-in, sign-up, password and two-factor settings pages, but no others. `ACCOUNT_PAGES` in `tests/e2e/test_accessibility.py` adds 21: the password-reset steps after the email, email confirmation, the two-factor code at sign-in, signing out, reauthenticating with a password or a code, setting a password on an account made by single sign-on, setting up an authenticator app, recovery codes, passkeys (the list, adding, editing and removing one), an inactive account and a failed SSO sign-in. Pages that want a recent sign-in are opened after signing in through the real forms (the `sign_in_with_password` fixture), and the test fails if a page sends the browser anywhere else, such as back to sign in. Two problems turned up, both on the passkey list. allauth's template loads Django's `humanize` tags, which weren't installed, so the page was a server error for anyone with a passkey; `django.contrib.humanize` is installed now. And its column of Edit and Remove links had an empty header; Sympraxi's copy of the template names the column for screen readers and puts each key's name in its links. Not covered: the SSO sign-up page, which allauth shows only when a provider's sign-in lacks something it needs, and signing in with a passkey, which happens in the browser's own dialog.

**Forms with errors are axe-tested.** axe saw each page only as it first loaded. `FORMS_WITH_ERRORS` fills in and sends forms the way a person would and runs axe on the page that comes back: sign-up with a short password, sign-in with a wrong one, the booking page without the required intake answers, and a demographic question marked required. Each form passes the browser's own checks for required fields, so the errors tested are the ones the server sends back.

**People change their own name and pronouns.** Only a site administrator could, in the Django admin, so a student whose name or pronouns changed had to ask someone. Account now opens on Name and pronouns (`accounts:profile`), for everyone signed in. It changes the full name, the preferred name and the pronouns and nothing else; the email address keeps allauth's page and its confirmation step. Each change is recorded as `auth.profile_changed`, naming the fields that changed but not what they said before or after, like the other account events. The full name stays editable for accounts made by single sign-on too: Sympraxi copies it from the provider only when it creates the account, so a sign-in never overwrites a change. The page is on the axe list, and on the list of forms sent back with errors, with a blank full name.

**Backups still leave out the two settings files.** `deploy/.env` holds the key that decrypts the two-factor secrets, and `deploy/backup.env` holds the restic password. A backup that carried them would carry the keys that protect it, and anyone holding one backup folder would have everything needed to read it. So `backup.sh` still leaves them out, and install.md now says to keep a copy of both away from the server, what each holds, what a restore onto a new server needs, and how to change the secret key and the database password. `install.sh` now makes `backup.env` readable only by its owner, as it already did `deploy/.env`.

## Phase 1: session-report questions and surveys (October 2026)

**Report answers belong to the record.** A center has one set of session-report questions, built like its other forms. They show on the record form below the fixed fields, and the tutor answers them. Each record has at most one response (`Response.record`), about the record's student, stored by question and option key like every other answer, so reports can count them across versions.

**Drafts replace their answers; final records amend them.** There were two ways to let a draft's answers change: a new response on every save, or an exception to the append-only trigger for drafts. Sympraxi takes the exception (forms migration 0004). While a record is a draft, each save deletes its response and writes a new one on the version the center asks now. A new response per save would have kept, permanently and in the FERPA export, answers a tutor changed before finalizing, while the record's own draft text is simply overwritten; and every report would have had to find the latest response for each record. Once the record is final, the trigger refuses any change to its answers unless the transaction has opened an amendment for that record, the same test records migration 0002 uses. `services.amend()` changes the answers in place, on the version they were given in, and keeps each changed one in the amendment under `answer:<question key>`, with the question and the answer before and after in words. The response itself never changes, and a final record can't gain a second one.

**Finalizing needs the required questions that show.** A required follow-up counts only when its condition is met. On a draft, required questions are marked "needed to finalize" and not refused, like the summary. An amendment keeps them required. Questions taken out of use aren't asked and aren't needed.

**An amendment asks the version the record was answered in.** A draft moves to the version asked now, filled in from its earlier answers by key. A final record keeps its version: an amendment corrects what was recorded, so it doesn't ask questions added later, and a record finalized before the center had questions gets none on its amend page.

**Staff only, unless a question says otherwise.** Staff who read the record (`records.view`) see every answer; front desk staff, who see only whether a record exists, see none. A director can mark a question "the student sees the answer", and the student then sees it with the summary on My writing. The student sees an answer only if its question was marked when the tutor answered and the latest published version still marks it, so marking a question later never shows students what a tutor wrote for staff. Each staff read of a record page or record form names the record's response in its `records.record_viewed` event. The FERPA export (format version 3) includes every answer, marked or not.

**Group copies get the answers.** Like the summary, next steps and topics. Each copy stays a draft for the tutor to read and finalize.

**Surveys are always anonymous.** The plan said anonymous by default. There is no setting for a named survey: its answers would be an education record with their own readers, export and audit, and no center has asked for one. The database refuses a survey response that has a student, appointment, record, person who answered or time (forms migration 0004), so adding named surveys later has to be a deliberate change.

**What a stored survey response keeps.** The form, the version, the center, the answers and the date in the center's time zone. Not the time. The invitation (`SurveyInvitation`) is never changed when its link is used, not even locked: a row lock would leave the answering transaction's ID on the invitation's row. The used link goes in `UsedSurveyToken` under a second hash of the token, which can't be matched to the invitation's hash without the link. The survey page writes no audit event, session or message, and doesn't look at who is signed in. `/survey/` is outside the staff two-factor gate, so a staff member who is also a student isn't redirected with the link in a query string.

**The token is never stored.** The scheduler writes the invitation and queues a task with its ID. The worker makes the token, stores its SHA-256 and sends the email through the delivery mailer directly, in one transaction. The queued mailer keeps each message's text in the task table, link included, and with the link anyone reading the database could find both the invitation and the used-link digest. If the relay refuses the email, the hash is rolled back and running the task again sends a new link. One consequence: survey emails need the task worker even when `SYMPRAXI_QUEUE_EMAIL` is off.

**What anonymity doesn't cover.** Someone with direct access to the database can see the order rows were written in (PostgreSQL's transaction IDs). Like the records' triggers, this doesn't stop whoever runs the database. Sympraxi's own pages and exports never show a single response, or a response with its date. For the reports still to come: don't list or export survey answers in row order or with their IDs.

**Survey links stay out of the logs.** Gunicorn's access log records each request with its time, and Django logs the path of every 404, so a used link opened again would land there too. With the database, either could match a response to its link. Both logs now write `/survey/[link]/` in place of the token, in the request line and the Referer header (`sympraxi/core/logs.py`; Gunicorn gets it through `--logger-class` in the Dockerfile). Turning the access log off would also have closed this, but it would leave an installation with no record of requests when something goes wrong. The CI smoke test opens a survey link on the real stack and fails if its token shows up in the `web` service's output. Caddy writes no access log in our Caddyfile; a campus that turns one on should scrub `/survey/` paths there too.

**Who gets a survey and when.** A center setting: when the tutor finalizes the student's record (the default), or from 30 minutes to a day after the appointment ends. Only students marked as here get one, so never for a canceled appointment, a no-show or a student who left a group. A student no one has marked gets none until they are marked, and finalizing a record marks them. Placeholders and meetings that weren't booked get none. The schedule's own survey goes out if it has one in use, otherwise the center's default. The scheduler looks back two days, so it catches up after an outage but never surveys a term of history after an upgrade. Students turn survey emails off under Account, Email reminders.

**Each invitation goes out once.** The invitation is unique per appointment and student and is written in the same transaction as its queued task, like reminders; a test races two sweeps. The link works once, for 14 days.

**Dead links look alike.** Unknown, used, expired, malformed, or for a survey that was stopped: the same 404 page, byte for byte apart from the CSP nonce. The URL inventory has a new "token" class for pages opened by a secret in the URL, with tests that a working token opens the page whether or not someone is signed in, and that every kind of dead token gets the same answer. Calendar feeds will use the same class.

**Results by term, from five responses.** Only directors see them (`forms.view_survey_results`). Answers are counted by question and option key across every version and shown in the latest wording; written answers are sorted, so their order says nothing about when they were given. A term shows nothing until at least five people have answered in it. The periods are terms, not any range of dates: a response counts in the latest term that started on or before the day it was given, so no two periods overlap and comparing them can't single out one response. Results aren't split by schedule or tutor. Responses don't record the tutor, because at a tutor with a few sessions a week the students would be easy to pick out. Reading results isn't audited, since no student can be identified from them; changing when surveys go out is.

## Phase 1: forms, intake and registration (October 2026)

**Questions and options have permanent keys.** A form's wording lives in numbered versions. Every question has a key that stays the same in every version, and so does every option of a choice question. Editing a published form starts a draft that copies it, keys and all, so moving a question, rewording it or rewording an option never changes what earlier answers mean. A question removed from a later version keeps its key in the versions that had it. WCONLINE stores answers by question number, which is why reordering or changing a question there scrambles past data.

**Answers are rows, stored by key.** A response is one person's answers to one version. Each answer is a row with the question's key, a typed value (text, a number, a date) and, for choices, the keys of the options chosen. Each answer also points to the exact question row it answered, so it is always shown with the wording the person saw, and the export lists both the words and the keys. The answers are rows, not one JSON document per response, because the reports still to come count answers by key and option key across every version, and because a database trigger can guard rows the way the records' triggers do. Questions skipped, or hidden because a condition wasn't met, have no row.

**A published version never changes, and answers are never edited.** A trigger (forms migration 0002) refuses any change to a published version, its questions or its options, and refuses adding to them. Publishing a draft is the last change a version takes. A response must answer a published version of its own form, and an answer must belong to a question in that version, under that question's key, choosing only that question's options. Responses and answers are append-only: changing answers means a new response, and the earlier one stays. A future retention purge will set `sympraxi.forms_purge`. As with the records' triggers, the database owner can still get around this.

**A question's kind of answer is fixed once it's published.** Until then a director can change it. After that, a short answer that became a date would mix two kinds of answers under one key, so the builder says to remove the question and add a new one, which gets a new key. A choice question needs at least two options with different wording. A yes or no question always offers Yes and No.

**One simple condition per question.** A follow-up shows only when one earlier choice question was answered with one of its options. It has to come after that question: the builder won't move it above, won't remove that question or option while the follow-up depends on it, and won't publish a version where the condition points anywhere else. Conditions refer to keys, so they carry over to new versions.

**Follow-ups work without JavaScript.** Each page carries a hidden list of the questions it showed. When the answers posted call for a follow-up the page didn't show, nothing is saved: the page comes back with the follow-up and says so (the "Continue" step). A Continue button does the same on purpose. With htmx, changing a choice that has follow-ups posts the form with `continue` set, and the questions are swapped in place; focus stays on the choice, and a status line says how many follow-ups appeared or went. An answer to a question that ends up hidden is dropped, so a response never holds an answer to a question the person didn't see.

**Directors reorder with buttons.** Each question in a draft has Move up and Move down buttons (WCAG 2.5.7, no dragging). Without JavaScript the page reloads with the question in its new place. With htmx the list is swapped in place, focus stays on the button, and a status line says what moved. At the top and bottom of the list the button stays focusable and is marked `aria-disabled`, so focus never falls off the page. Options are reordered with a Place menu on the question's page instead: move buttons inside that form would be the first submit button, so pressing Enter in a text field would move an option instead of saving.

**Registration is asked once, at the first booking.** A center has one registration form. A student who hasn't answered it sees its questions on the booking page, above the intake questions, and the booking and both sets of answers are saved together or not at all. A new version isn't asked again; students see and change their answers under "Your registration answers," and each change is a new response. Staff booking for a student aren't shown it.

**Intake: the schedule's own form, or the center's default.** A schedule with its own intake form in use asks it; every other schedule asks the center's default form. A form taken out of use isn't asked, and its answers are kept. Intake answers belong to the appointment, so they stay with it when it moves. In a group, each student answers for themselves and sees only their own answers. A weekly series booked by staff gets a copy of the answers on each appointment. Students can change their answers, as a new response, until the appointment starts.

**Staff can fill in the intake or skip it.** On the staff booking page every intake question can be left blank, which skips the form; answering any of them makes the required ones required again. A skipped form can be answered later by the student from the appointment page. Staff answers are recorded as theirs (`answered_by`), about the student.

**Demographic questions are always optional.** A question marked as asking about who the student is (for example gender, race or ethnicity, age, or first-generation status) can't be required; a check constraint in the database holds to that. Directors decide which questions those are.

**Who sees the answers.** Intake answers: the appointment's tutor, front desk staff and directors (`forms.view_intake`), on the appointment page and in the pre-session brief. Registration answers: directors see them all (`forms.view_all_registration`); tutors, for students they tutor, and front desk staff see only questions a director marked for staff (`forms.view_registration`). The current published version decides which questions those are, so unmarking a question hides the answers already given to it, and a question dropped from the form is seen by directors only. The question itself tells students when only directors see their answer. Students see all of their own answers (`forms.answer_own`). Every staff read is audited (`forms.answers_viewed`) with the student and the responses shown, never the answers; students reading their own aren't. Site administrators get none of these actions. Only directors build forms (`forms.manage`); adding a form, publishing a version and starting or stopping a form are audited.

**The FERPA export includes every answer.** Registration answers and each appointment's intake answers, earlier responses too, each in the wording of the version answered, with the option keys. The export format is now version 2.

**Room for the slices still to come.** The models already have the session-report and survey kinds, and a response's student is optional for anonymous surveys. The append-only trigger will need an exception for session-report answers on draft records, or each draft save can be a new response; locking them on final records can follow records migration 0002 (done in the next slice, above). Reports can count answers by `Answer.key` and by the option keys in `Answer.options`, across every version of a form. File-upload questions wait for the upload hardening planned for Phase 2.

## Phase 1: first-Monday load test (October 2026)

**The load test books through the real pages.** Virtual students and front desk workers open the schedules page, list open times, open the booking page and post its form over HTTP. The server uses the production settings without HTTPS and runs three web workers, as the Dockerfile's Gunicorn does, with the task worker and the scheduler beside them. Calling `services.book` in a loop would have skipped the work that costs the most, which is listing open times and drawing pages, and it couldn't show whether a refusal reaches the person as a message. Gunicorn doesn't run on Windows, so `tests/load/server.py` starts three processes that share one socket and each answer one request at a time, which is how Gunicorn's sync workers behave. Everyone starts signed in, with a session row each, so the run measures booking and not password hashing. `docs/development.md` says how to run it.

**The checks don't use the booking code.** `tests/load/check.py` reads the tables with SQL and works out each rule again: no tutor or student double-booked, no group over its size, no tutor cap or student limit exceeded, notice and horizon kept, every appointment inside its tutor's hours. Limits are replayed in booking order. A schedule whose limits count every schedule in the center can end the day over its limit with no booking breaking it, because a booking on another schedule is held only to that schedule's limits. The checker also compares the database with what each person saw: every appointment someone was shown as booked exists, and nobody holds one they weren't told about. Every refusal has to show a message. A server error, a dropped connection or a refusal without a message fails the run.

**Acceptable means a p95 under 1 second and a p99 under 2 seconds on every page.** Times are measured at the client, so waiting for a free worker counts. One second is the limit Jakob Nielsen gives for a response that doesn't interrupt the person's train of thought.

**Results on October 15, 2026.** Measured on a Windows 11 laptop with 8 logical processors and PostgreSQL 18.6 on the same machine, which was running other tests at times, at commit 9462a27 plus another session's uncommitted form-builder work (the seeded center has no booking questions). The standard run went twice: 500 students arriving over ten minutes, 150 of them in the first minute, while three front desk workers booked for students. Both passed. The first made 1,147 booking attempts (661 booked, 486 refused with a message) and the second 1,213 (656 booked, 557 refused), with no errors in either; 487 and 481 students got at least one appointment. There were no server errors or deadlocks, and every check passed. Every page's p95 was under 600 ms. Its p99 was under 800 ms in the first run and under 1.5 seconds in the second, which shared the processor with another session's browser tests. Nearly all the waiting came in the first minute, when requests averaged 56 a second (static files included) and the p95 across pages was 593 ms and then 808 ms. After that it stayed under 200 ms. Open times cost the most to draw: a day on the in-person schedule is about 98 KB of HTML, one row per tutor per time.

**Three workers ran the rush at about 90 percent of what they can serve here.** The same 500 students with no pauses between pages, arriving over two minutes, held three workers at about 62 requests a second, their limit on this machine. The median page then took 2 seconds, and Windows refused 168 connections once the listen backlog was full (behind Caddy they would probably have waited instead). The rush above averaged 56 a second in its first minute and reached 63 over ten seconds. With eight workers the same hard run passed, with every p95 under 250 ms. Static files were 42 percent of all requests, because each student's first visit loads the stylesheets, scripts and icons through the same workers. An installation now sets the number of workers, and static files stay with WhiteNoise; see "Phase 1: sign-in limits and web workers", above.

**The per-tutor locks cost nothing visible at this size.** PostgreSQL recorded no deadlocks in any run. Sampling `pg_stat_activity` two to five times a second, a query waiting on a row lock appeared in 3 of 4,409 samples across the two standard runs and in 7 of 563 in the hard run with eight workers, never more than one at a time. Most waited on a student's membership (one student, two requests); the rest waited on tutor assignments. The booking form's p50 was close to the open-times page's (84 ms and 81 ms). The lock order in "Row locks in a fixed order" stays as it is.

**Found and not fixed, because each changes what people see:**

- Open times still list tutors who have reached their daily or weekly cap, and the booking form then refuses with "This tutor is fully booked that day." That was 235 of the 486 refusals in the first run and 283 of 557 in the second, and some students got it on every try. Leaving those times out of the list wouldn't change the rule itself.
- A double-click books the time and then tells the student it failed. In every double-click where one request booked (34 in the first run, 31 in the second), the other was refused. In the first run that was "Someone else just booked that time." 21 times, "That time isn't open anymore." 8 times, and the student's own name followed by "already has an appointment then." 5 times. A browser shows the answer to the last click, so a student can be told the time is gone while holding it. The booking page could notice that the student already holds that time and show the appointment, and the button could turn off after the first click.
- All password sign-ins share one rate limit. allauth allows 30 sign-ins a minute from one address. Behind Caddy every request arrives from Caddy's address, and `ALLAUTH_TRUSTED_PROXY_COUNT` isn't set, so the 30 cover every student at once. A campus network behind one public address has the same effect. Of 150 password sign-ins in one minute, 30 got in and 120 got allauth's bare "Too Many Requests" page, since Sympraxi has no 429 template. Setting the proxy count to 1 when `SYMPRAXI_TRUST_X_FORWARDED_FOR` is on, raising the per-address limit and adding a 429 page would fix it. New accounts have their own limit of 20 sign-ups a minute per address, which should behave the same way (not tested). Single sign-on doesn't go through the sign-in limit.
- Limit messages say "the limit of 1 appointments a day", and front desk refusals start with the date even for a single booking.

All four are fixed: the first, second and last in "Phase 1: booking page fixes after the load test" and the sign-in limit in "Phase 1: sign-in limits and web workers", both above.

## Phase 1: attendance, blocks and reminders (October 2026)

**Attendance belongs to each student, not to the appointment.** In a group, some students come and some don't, so attendance is kept on `Participant`: came, no-show, or not marked, with who marked it and when. The appointment keeps its two statuses ("Two statuses and three flags", below). A no-show still held the tutor's time, so its appointment stays scheduled and the overlap constraint needs no change. A late cancellation is an ordinary cancellation that frees the time, with `late_cancel` set on the student's row. Adding "completed" or "missed" statuses to the appointment would have had to say something about the whole group, and would have mixed what happened to the time with what happened to each student.

**A final session record means the student came.** Finalizing a record marks its student as here, and a student with a final record can't be marked a no-show. A record finalized after a no-show was confirmed overrides it, since the record shows the session happened. Records finalized before this slice were marked by records migration 0003.

**Possible no-shows are flagged, never decided.** Each schedule sets a grace period, 15 minutes by default. Each minute the scheduler flags any student no one has marked by then. A flag only asks staff to check: they confirm the no-show, mark the student as here, or clear the flag, and nothing counts until they do. Tentative appointments, placeholders, and students with any session record, even a draft, aren't flagged. The sweep looks back two days, so an upgrade doesn't flag a term of unmarked history; staff can still mark older appointments by hand. Tutors mark appointments they teach; front desk staff and directors mark any. A confirmed no-show sends the student a short email that says the session was recorded as missed, gives the count for the term, says what happens at the center's limit, and invites them to reply if they did come or something kept them away.

**Late cancellations are off until a schedule turns them on.** Each schedule sets a window, for example 120 minutes; a cancellation inside it is late. The window is separate from the change cutoff: with a 60-minute cutoff and a 120-minute window, a student can still cancel online between two hours and one hour before, and it's recorded as late. The cancel page warns them first. The student gets a late-cancellation email instead of the usual one. The tutor's email doesn't change. Staff canceling inside the window check "The student asked to cancel" when that's why; otherwise nothing is recorded, so a center never charges a student for its own cancellations. That box appears only for an appointment with one student, since one late cancellation can't belong to a whole group.

**Waivers keep the record and drop the count.** Front desk staff and directors waive a late cancellation or no-show with a reason. It stays on the student's record, and the export shows it with the reason, but it no longer counts toward a block. A waiver doesn't lift a block already in effect; that stays a director's decision. Like an exemption's note, the reason stays out of the audit log, which records who waived what and when.

**Blocks pause online booking, not the student.** A center sets limits that count every schedule; a schedule can set its own that count only that schedule and pause only that schedule. Each limit counts unwaived no-shows, or late cancellations, within the term of the appointment being counted, or from a date the director chooses. Counting is by the appointment's start, like the booking limits. When a no-show is confirmed or a late cancellation recorded, the check runs in the same transaction after the student's membership is locked, so two at once can't set two blocks or miss one (a test races two). A block ends after the last day of that term unless a director lifts it sooner. Lifting doesn't reset the count, so the next one past the limit sets a new block; to take one out of the count, staff waive it. While blocked, the student can't book for themselves, but their appointments stay and they can still cancel or move them; staff can book for them. The student sees why, when it ends, and whom to write to, on the booking pages and their appointments page. Setting and lifting are audited. Only directors see the list of blocks and lift them, because a block is a judgment about a student, like an exemption.

**Reminders are counted in real time and follow the appointment.** A schedule sets up to three reminders, from 30 minutes to 48 hours ahead; new schedules start with 24 hours and 1 hour. A reminder is due at the start minus its lead time in real hours, like notice and cutoff, so a day-before reminder across a daylight-saving change comes 24 hours ahead, which the clock reads as 23 or 25. The due time comes from the appointment's current start, so a moved appointment's reminders follow it, and the start time is part of what makes each reminder unique, so a moved appointment gets new ones. Canceled, tentative and placeholder appointments get none. A reminder that fell due before the appointment was booked, moved or confirmed is skipped, because the confirmation email just went out; so is a student's that fell due before they joined a group.

**Each reminder is sent once, enforced by the database.** The scheduler writes a `Reminder` row (appointment, recipient, lead time, start) and queues the email in the same transaction. A unique constraint on those four columns means a second scheduler, or a sweep run twice, inserts nothing and sends nothing; a test races two. The reminder also locks the appointment row, so a cancellation or move committing at that moment is seen. Reminders skip anything more than 15 minutes past due, so a scheduler that was down catches up on what is still close to on time and never sends a stack of stale ones. The shortest gap between two reminder choices is 30 minutes, so one sweep never sends two reminders for one appointment.

**Students opt out of reminders; tutors opt in.** The settings are on the account (Account, Email reminders), not per center, and every reminder links to them. A student's reminder names their tutor, the time and the place. A tutor's names no students; they sign in to see who it is. Reminders carry no calendar file, since the booking email already added the appointment.

**The scheduler is its own process.** `manage.py scheduler` sweeps at the start of every minute: reminders first, then possible no-shows. It runs as a fourth Compose service beside web, worker and db. The task worker runs jobs it is handed, and something still has to decide each minute which jobs are due; cron inside a container would need a second process manager. After each sweep that finishes without an error, the scheduler writes the time to a heartbeat file, and `python -m sympraxi.healthcheck scheduler` is healthy only if that time is under three minutes old. A scheduler that can't reach the database writes nothing and turns unhealthy, not only one whose process died. `upgrade.sh` stops it while migrations run and `restore.sh` while the database is replaced. Links in reminders need `SYMPRAXI_BASE_URL`; the production stack fills it in from `SYMPRAXI_DOMAIN`, and the command refuses to start without it.

**The row-lock order gains a level.** Memberships, then tutor assignments, then the appointment, then its participants. Marking attendance and canceling (when a student asked) now lock the students' memberships first, because either can set a block.

## Phase 1: session records (October 2026)

**One record per student, in groups too.** A session record is about one student. A group appointment gets a separate record for each student in it, so no student can see what was written about another. To save typing, the form for a group can start drafts for the rest of the group with the same summary, next steps, topics, length and resources. Staff notes and the writing project aren't copied, because notes are about one student and each student has their own projects. Every copy stays a draft until the tutor reads and finalizes it, and each student gets their own email. Students who left the group get no copy. The alternative, one shared record per group, would have meant either hiding the summary from students or showing each of them what was written about the others.

**Final records are locked in the database.** As with the audit log, a trigger (records migration 0002) does the locking. Once a record is final, an UPDATE of it, or any change to its topic tags or attached resources, is refused unless the same transaction has opened an amendment for that record. `services.amend()` writes the `Amendment` (author, time, reason, and each changed field before and after), sets `sympraxi.amendment` to its ID for the rest of the transaction, makes the change, and clears the setting. Even inside an amendment, the student, tutor, appointment and finalization can't change. Final records can't be deleted, and amendments are append-only. A future retention purge will set `sympraxi.records_purge`. Anyone with a database shell can set either value, so the trigger stops silent edits made through Sympraxi's code or the admin. Like the audit log's trigger, it doesn't stop the database owner.

**What finalizing needs.** A summary for the student, at least one concern tag, and a session that has started. Stages and tutor actions are optional. When a tutor finalizes an incomplete record from the form, it's saved as a draft and the page says what's missing, so nothing typed is lost.

**Who reads records.** Tutors read the records of students they have an appointment with in that center: past or upcoming, but not canceled, and not a group the student left. Upcoming appointments count so the pre-session brief works. Tutors also read the records they wrote. A record for a meeting that wasn't booked doesn't open the student's other records to its tutor; otherwise any tutor could reach a student's history by starting a draft about them. Tutors edit and amend only their own records. Directors read, write and amend every record in their center, and only directors export. Front desk staff see whether a record is final, a draft or not written (on the appointment page, the day sheet and the records-to-write list), never what it says. Site administrators get none of these actions. A student sees only their own final records, and only the parts written for them. As with appointments, someone else's record is a 404 for people who can see some records, so record IDs can't be probed. The build plan lets directors widen or narrow tutors' access per center; that setting isn't built yet.

**Pages about a student use the student's membership.** The history, brief and export are about one student in one center, and the student's `Membership` holds both. Their URLs use the membership's UUID, so no name or student ID appears in a URL, and the policy gets one object that knows both the student and the center.

**Every staff read is audited.** Opening a record or its form, opening a student's history, and each pre-session brief shown on an appointment page write `records.record_viewed` or `records.history_viewed`, with the student's ID and which page it was. Saving, finalizing, amending (with the names of the fields changed), exporting and changing the settings are audited too. No event holds record text. Students reading their own records aren't logged, since that isn't a disclosure.

**Students see summaries, next steps and resources.** `Center.students_see_staff_notes`, off by default, adds the staff notes to the student's My writing page. Either way, the record form tells tutors that students can ask to see everything written there (34 CFR 99.10), and My writing tells students they can ask for a copy. Topic tags aren't shown to students; they're in the export. When a final record is amended, My writing shows the date it was updated but not the earlier text.

**The summary email says it's ready and links to it.** It names the tutor, the center and the date. `Center.summary_email_includes_text`, off by default, adds the summary and next steps. Staff notes never go in an email. The email goes through the queued mailer after the transaction commits, so a rolled-back finalize sends nothing. Amendments don't send another email.

**The FERPA export.** A director can export one student's complete record in their center, as JSON or as a page to print or save as PDF: account details, every appointment (canceled ones and groups the student left included), every session record (drafts included) with staff notes and each amendment's before and after, attached resources with the tutor's notes and each resource's license, and writing projects. Other students are left out (99.12): a group appointment shows how many students it had, never who. Each export is audited. The disclosure log (99.32) comes in a later slice.

**The catalog is loaded by a command.** `manage.py load_catalog` reads `catalog/vocabulary.yaml` and `catalog/resources/*.yaml` and matches on topic slugs and resource IDs, so a second run changes nothing and an edited entry is updated in place. Nothing is deleted. A resource that leaves the catalog is marked inactive, because records may still point to it, and a topic missing from the file is reported. One bad entry stops the whole load. Each resource keeps its license, publisher and (for OpenStax) the CC BY source it can be copied from. The catalog changes between releases without any change to the schema, so `install.sh` and `upgrade.sh` run the command every time, and so does `seed_demo`. The Docker image now includes `catalog/`. It needs PyYAML, the one new dependency.

**Topics and resources live in the records app for now.** The build plan's layout gives resources an app of their own. Today every use of a resource goes through a session record, so the two models share `sympraxi/records`; moving them out later is a matter of two models and their loader.

**Centers add links, not files.** Directors add their center's own resources: a title, an https address, their own summary, publisher, license and topics. Those links are offered only in that center and come first when a suggestion ties. File uploads wait for the upload hardening planned for Phase 2.

**Suggestions follow the concerns.** A resource scores 3 for each concern it shares with the record. One that shares none scores 2 if it has a more specific term under one of the record's concerns (record: `citation`, resource: `citation:apa`), or else 1 if it has a related term (the parent, or another term under the same parent). Related terms don't add to a shared one, so a page tagged both APA and MLA doesn't outrank an APA page on an APA record. Each matching stage or action adds 1, but a resource needs a concern point to be suggested at all, because nearly every resource fits "drafting" or "revising." The top eight show.

**The record form works without JavaScript.** Attach and Search are submit buttons in the form. Without htmx they post the form back and redraw it, unsaved and without error messages. With htmx, checking a topic refreshes the suggestions, the search updates as the tutor types, and Attach adds the resource in place; each request sends only the fields it needs (`hx-params`), so the notes never travel with a search. A status line announces what changed. Resource links on the form open in a new tab and say so, so following one doesn't lose an unsaved record. Concern terms are grouped under their parents in `<details>` elements, which work by keyboard with no script.

**Writing projects are basic.** Tutors start a project from the record form, and the tutor or a director can edit it or mark it finished. Students can't add or edit their own projects yet.

**Records stay out of the Django admin.** The admin is for site administrators, who have no access to records, so none of the records models are registered there.

## Phase 1: single sign-on (October 2026)

**One Entra tenant and one Google domain per installation, set in the environment.** The build plan had each center entering its own tenant's settings. An installation serves one college, though, and a college has one tenant or one Workspace domain. Reading providers from `SYMPRAXI_ENTRA_*` and `SYMPRAXI_GOOGLE_*` variables keeps client secrets out of the database and its backups. allauth's admin screens for apps and tokens are removed, and an app saved in the database is ignored. A provider with only some of its variables set stops the site from starting, rather than quietly leaving SSO off.

**allauth's generic OpenID Connect provider for both.** allauth's Microsoft provider reads the Graph profile, whose `mail` field isn't verified and which carries no tenant or `amr` claim. The generic provider reads the ID token, which has everything the checks need. Userinfo isn't fetched, PKCE is on, and tokens aren't stored. The sign-in URLs are `/accounts/oidc/entra/...` and `/accounts/oidc/google/...`.

**The tenant is pinned three ways.** The discovery document is the tenant's own (`/{tenant}/v2.0`), so allauth rejects ID tokens from any other issuer. `common`, `organizations`, `consumers` and anything that isn't a GUID are refused at startup. `sympraxi/accounts/sso.py` also checks `tid` and `iss` on every sign-in.

**Only addresses the provider vouches for.** Entra's `email` claim is unverified and editable, the hole behind the 2023 "nOAuth" account takeovers. Sympraxi requires Entra's `xms_edov` claim (the address is in a domain the tenant verified), and Google's `email_verified` plus a matching `hd`. When `SYMPRAXI_SIGNUP_EMAIL_DOMAINS` is set, the address must be in it. The checks run on every sign-in, so an account that stops passing them can't keep using SSO.

**Linking by address, with two limits.** A sign-in that passes the checks is linked to an existing account with the same address. After that, sign-ins match the provider's subject ID, so a later change of address doesn't break the link. An account already linked to a different identity at the same provider is never linked again by address: colleges reuse addresses, and a new holder must not inherit the old holder's records. allauth removes the password of a matched account whose address was never verified, so whoever registered it first loses access. Links, unlinks and refused sign-ins are audited (`auth.sso_linked`, `auth.sso_unlinked`, `auth.login_failed` with a reason).

**SSO doesn't skip the staff 2FA rule unless the token proves MFA.** By default allauth's two-factor step runs after SSO like after a password, and staff without a second factor are sent to set one up. `SYMPRAXI_TRUST_IDP_MFA` accepts the provider's MFA only when the ID token's `amr` claim contains `mfa`. Nothing else counts, including Google's `hwk` and `swk`, whose meaning as multi-factor Google doesn't define. Entra sends `amr` once it is added as an optional claim. Google began sending `amr` in June 2026, on request, and only to apps it has verified, so an Internal Workspace app may never receive it; those installations keep Sympraxi's own 2FA.

**SSO-only is enforced at sign-in, not in the template.** `SYMPRAXI_SSO_ONLY` hides the password form, passkey button and sign-up link. `AccountAdapter.pre_login()` refuses every non-SSO sign-in except a site administrator's, from any page. Site administrators keep a break-glass password page at `/accounts/login/local/`, with two-factor login as usual. Without a provider, the setting is refused at startup and ignored at runtime, so it can't lock everyone out.

**SSO buttons are forms, and form-action allows the provider.** Starting sign-in takes a POST, so a link on another site can't start one. Browsers apply the Content Security Policy's `form-action` to the redirect that follows a form, so the policy adds `https://login.microsoftonline.com` or `https://accounts.google.com`, only for providers that are set up. A browser test presses each button from the keyboard and checks that the browser then requests the provider's page, which it does only if the policy allows the redirect. The test browser resolves no host but localhost, so that request, like any other a page might make, never leaves the machine. Playwright can't intercept a request made while following a redirect, so blocking name lookups is the only dependable guard.

**Plain text buttons, no logos.** "Sign in with Microsoft" and "Sign in with Google" use the standard USWDS button. Vendor logos would put trademarked artwork in the repository for no gain in clarity.

## Phase 1: scheduling core (October 2026)

**No double-booking, enforced by PostgreSQL.** An exclusion constraint (`scheduling_appointment_no_tutor_overlap`) rejects two active appointments for the same tutor whose times overlap, on any schedule in any center. The `=` on the tutor column needs the `btree_gist` extension, which the first scheduling migration creates. It is a trusted extension, so the database owner can create it without superuser rights. The booking service checks first so people get a readable message; the constraint catches the race that check can't.

**The break after an appointment is stored on the row.** Each appointment keeps `blocked_until`, its end plus the schedule's buffer at booking time, and the constraint covers `[starts_at, blocked_until)`. The constraint can't add the buffer itself: adding an interval to a `timestamptz` isn't an immutable expression, so PostgreSQL won't index it. Changing a schedule's buffer later leaves existing appointments as they are.

**Row locks in a fixed order.** Booking, changing and canceling each run in one transaction and lock rows in the same order: the students' memberships (their limits and their own calendars), then the tutor assignments by primary key (caps and group seats), then the appointment. Two students racing for the last seat in a group, or one student booking twice at once, can't both get through. The locks use `select_for_update(of=("self",))`, so joined rows such as the center stay unlocked and bookings across a center don't queue behind each other. A booking or a move locks every assignment its tutor has, on every schedule, not only the one being booked. With only that one locked, two students booking one tutor on two schedules at the same moment could both insert, and PostgreSQL stopped one with a deadlock while checking the exclusion constraint; that student got a server error. Now the second booking waits for the first to commit, sees it and is refused. Bookings for one tutor queue even when their times don't overlap, but each holds the locks only for its own short transaction. The constraint stays as the backstop: if it, a deadlock or a serialization failure still stops a booking or a move, the person is told the time was just taken.

**Wall-clock times on daylight-saving nights.** Weekly hours and opening hours are wall-clock times in the center's zone. A wall-clock time stands for the first instant at which the clock reads that time or later. On the night clocks go back, 1:30 means the first 1:30; on the night they go forward, 2:30 means 3:00. Slots step in real time from the opening instant, so the repeated hour gets its own slots and every appointment lasts as long as it says. A weekly series keeps its wall-clock time each week. Notice, horizon and cutoff are measured in real time.

**Limits count by the appointment's start, in local time.** A day is a local calendar day (23 or 25 hours on switch days), a week runs Monday to Sunday, and a term is the schedule's term dates. Canceled appointments and placeholders don't count. When "count appointments on every schedule" is checked, a schedule's limits count the student's appointments on all of the center's schedules; each schedule's own limits apply when booking on it.

**Exemptions cover appointments, not booking days.** An exemption lifts a student's count and minute limits for appointments on or before its last date, so the last day of an exemption can't be used to book a month ahead. Notice, horizon and cutoff still apply. Every exemption has an end date. Adding or ending one is audited, without the note.

**Staff book under different rules.** Front desk and directors aren't held to minimum notice, the horizon or the change cutoff, so they can enter walk-ins and fix mistakes. They are held to student limits and tutor caps unless they check "book even if it goes over," which the audit log records. Nobody can book outside a tutor's hours or over another appointment.

**Students move their own one-to-one appointments; staff move groups.** Until the change cutoff, a student who is the only person in an appointment can move it to another open time on the same schedule. The move keeps the appointment's row and calendar UID, raises its `SEQUENCE`, and re-checks every booking rule while leaving the appointment itself out of the counts. Moving to another schedule means canceling and booking again. Only staff move group appointments, because a move changes the time for everyone in the group. Moving has its own policy action, `scheduling.change_appointment`, granted like canceling.

**Grants that reach only a person's own records.** Students can view, cancel and move only the appointments they are in, and tutors can view only the appointments they teach. These limits are `OBJECT_RULES` in `policy.py`, beside the role grants, and `tests/test_policy_matrix.py` lists them by hand. Someone else's appointment returns 404, as it does for an outsider, so appointment IDs can't be probed. Students never see other students: open times carry no names, and only staff and the tutor see who is in a group.

**Site administrators get no scheduling actions.** Appointments are student records, so the Phase 0 rule holds: they are reached through a center role, not through `is_superuser`.

**Two statuses and three flags.** An appointment is scheduled or canceled. Walk-in, placeholder and tentative are flags on a scheduled appointment, and a tentative booking holds its time until staff confirm or cancel it. The constraint ignores only canceled appointments, so a status added later that still holds the time (completed, missed) is covered without a migration.

**Extra hours stay inside opening hours.** A tutor's extra hours can add time on a day they don't usually work, but never past the schedule's opening hours. A center that stays open late for finals changes the schedule's hours.

**Appointment emails say as little as possible.** A student's email names their tutor, the time and the place. A tutor's email says a student booked and links to the appointment, without the student's name. Mail goes out after the transaction commits, so a booking that is rolled back sends nothing. `SYMPRAXI_BASE_URL` sets the links in mail sent outside a page request, such as the reminders still to come.

**Calendar files are written by hand.** An appointment needs about a dozen iCalendar properties, and the rules that matter (escaping, CRLF line endings, folding at 75 octets) fit in one short module, so there is no `icalendar` dependency. Each appointment keeps one UID. Bookings and changes go out as `METHOD:PUBLISH` with a rising `SEQUENCE`, cancellations as `METHOD:CANCEL`. Calendar apps vary in how they handle these, so the email text is the record. The queued mailer now carries attachments, as text or as base64 for binary files.

**Property-based tests with Hypothesis.** A state machine books, cancels and moves appointments at random on two schedules that share a tutor, across a daylight-saving week, and checks the tables after every step: no tutor or student is double-booked and no limit, cap or group size is exceeded. The checks are computed independently of the booking code. The default run plays the same sequences every time, so CI is repeatable, and it fails if those sequences never book, cancel, move or reach a limit, so it can't pass by being refused everything. `HYPOTHESIS_PROFILE=thorough` plays about twelve times as many, chosen at random. A separate test races real threads in committed transactions.

**PostgreSQL 18 for local tests on Windows.** The pgserver package's PostgreSQL has no contrib extensions, so it can't create `btree_gist`. The local runs for this phase used the EDB PostgreSQL 18.6 binaries zip, started from a scratch folder on its own port. The `postgres` Docker images and the Debian and Ubuntu packages include `btree_gist`.

## Phase 0 (October 2026)

**Django 6.1 now, Django 6.2 LTS before the pilot.** The build plan first said "5.2 LTS now." Moving from 5.2 to 6.2 crosses a major version. Moving from 6.1 to 6.2 is a single feature release, and 6.2 LTS ships in April 2027, before the summer pilot. Django 6.x also brings two things Sympraxi would otherwise need packages for: a built-in Content Security Policy with nonces, and the Tasks framework. Renovate is set not to jump to 6.2 automatically.

**Background jobs: Django's Tasks framework with the `django-tasks-db` backend.** Jobs are stored in PostgreSQL and run by `manage.py db_worker`, so a small install needs no Redis or Valkey. The jobs are written against `django.tasks`, so a different backend can be swapped in later without code changes.

**Email through `MAILERS` (new in Django 6.1).** The `default` mailer hands messages to the task worker. The `delivery` mailer talks to the campus SMTP relay. A slow relay never holds up a page.

**Shared cache in the database.** Login rate limiting needs a cache that all Gunicorn workers share. Django's database cache does that without another service. Set `CACHE_URL` to a Valkey URL if a large install needs it.

**Design system: U.S. Web Design System 3.14.** It is built and tested for accessibility, and its code is in the public domain (CC0); its fonts are under the SIL Open Font License and its icons under Apache 2.0. We use its components and styles but not the U.S. government banner or anything that implies a government site. GOV.UK Frontend was the alternative; its typeface and crown are restricted to UK government services.

**Assets are copied from npm packages, not loaded from a CDN.** A self-hosted install makes no third-party requests, which keeps the Content Security Policy at `'self'` and keeps students' browsing private.

**Server-rendered pages with htmx.** Less JavaScript, fewer accessibility traps, a smaller attack surface. htmx is configured with `allowEval` and `allowScriptTags` off and without its inline indicator styles, so it works under the strict CSP.

**Permissions in one module.** `sympraxi/core/policy.py` holds every rule. A hand-written test matrix and a URL inventory test keep it honest. Outsiders get 404 rather than 403, so URLs can't be used to discover which centers or records exist.

**Site administrators are not a back door to records.** Superusers get operational actions only (`SITE_ADMIN_GRANTS`). Actions that read student records will be granted by center role, never to site admins by default.

**The audit log is append-only in the database.** A PostgreSQL trigger rejects `UPDATE` and `DELETE` on `privacy_auditevent`. A future retention purge will set `SET LOCAL sympraxi.audit_purge = 'on'` for its own transaction. The actor and center are stored as IDs without foreign-key constraints, plus a text label, so deleting a person or center never rewrites history.

**Two-factor login required for every staff role.** Tutors, front desk, directors and site admins are sent to the 2FA setup page until they add an authenticator app or a passkey. Text-message codes are not offered. The Django admin uses the same sign-in, so the same rule applies there.

**Python 3.12 in Docker and CI**, matching development machines. Security support for 3.12 runs to October 2028.

**PostgreSQL 18 in production and CI.** The local test run on Windows used a portable PostgreSQL 16 because Docker wasn't available. Nothing in Phase 0 depends on 18.
